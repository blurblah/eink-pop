## 관찰과 확인

사용자: 방이 바뀌면 초기 톤처럼 보이고 전체 정리 후 의도한 톤으로 바뀐다. 정리 전에 움직인 인물·물체 자리만 다른 톤으로 남는다. 짧은 클립에서 잔상이 없었던 결과만으로 다른 방의 화질을 보장할 수 없음을 확인했다.

- 입력: 실제 게임320×200 →640×400, shadow_v1(60/128/213), NORMAL2ms/직접 전이 최대13주사, v8앱bae7bdd8, 드라이버ffeea2a.
- 송신2043장 전체의 패킷 CRC·압축 복원·bitmap SHA-256이 호스트 기록과 일치. 완료 ACK는2042장뿐이다. 전체에서shadow_v1 사용, 방 전환별 톤 분기는 호스트 변환 코드에 없다.
- 주기 정리8회 직전/직후 입력 픽셀 일치율은98.733~99.945%. 정리가 다른 보정 이미지를 선택하는 코드도 없다. 보드의 정리는 드라이버·이전 이미지·확대 버퍼를 흰색으로 동기화하고 같은 현재 입력을 다시 그린다.
- 화면20% 이상 변경된 전이는34개. 방 식별자가 없으므로 이를 방 변경34회라고 해석하지 않는다. 연속 두 장의 큰 변화도 있어 단순 변화량으로 전체 지우기를 넣으면 중복 깜빡임이 생길 수 있다.

## 유력한 설명과 미확정 사항

직접 전이는 이전 회색에서 다음 회색으로 가는 구동열을 선택한다. 전체 정리는 흰색 기준으로 되돌린 뒤 목표 회색을 그린다. 같은2bpp 목표 값이어도 실제 입자의 최종 위치/명암이 경로에 따라 달라질 수 있다. 변하지 않은 배경은 재구동하지 않으므로 오차가 남고, 움직인 자리만 다른 경로로 재구동된다. 이 설명은 사용자 보고와 전송 근거에 부합한다.

전송 데이터와 소프트웨어 경로가 같다는 사실은 광학 측정이 아니다. 카메라 없이 실제 밝기 오차를 수치화하지 않았고,13주사 단축/2ms/원본 직접 전이 중 어느 변경이 원인인지 확정하지 않았다. 원본19주사도 여러 방에서 같은 비교를 하지 않았다. 제품 불량이라고 판단할 근거도 없다.

## 다음 수정 방향

방이 확정적으로 바뀌는 시점에 전체 정리 후 새 방을 표시하면, 현재30초 주기 정리를 기다리는 동안의 톤 불일치를 줄일 가능성이 가장 높다. 이는 직접 전이 파형 자체의 해결이 아니라 방 전환 시 초기화하는 우회책이며, 방 이동마다 한 번 깜빡임과 지연이 추가된다. 같은 방 안의 명암 일관성까지 보장하지는 않는다.

구현 전 게임의 실제 방/레벨 식별자를 화면과 함께 원자적으로 추출할 방법을 확인한다. 입력 변경량만으로 방을 추정하거나 연속 로딩 화면마다 정리하지 않는다. 주기정리와 방 전환 정리가 겹치면 한 번만 수행해야 한다. 전이별 파형 재조정은 별도 후보로 남기며 이번 조사에서는 변경하지 않았다.
