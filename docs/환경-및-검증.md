## 환경 분리와 재현

전역 Arduino 환경을 바꾸지 않고 다음 위치를 사용합니다.

- 설정: `.local/arduino-cli.yaml`
- 코어·도구·패키지 인덱스: `.local/arduino/data/`
- 다운로드: `.local/arduino/downloads/`
- 스케치북: `.local/arduino/user/`
- 캐시: `.local/arduino/build-cache/`
- 공식 드라이버: `.local/libraries/LilyGo-EPD47/`
- 빌드: `.local/build/first_image/`

`.local/`과 `artifacts/`, 자격증명 파일은 `.gitignore`로 제외합니다. 초기화 직후 `git check-ignore`로 백업·로그·환경 설정·`.env` 제외를 확인했습니다.

다시 환경을 만들 때 프로젝트 루트에서 다음 변수를 설정합니다.

```sh
EINK_ROOT="$PWD"
EINK_CLI='/Applications/Arduino IDE.app/Contents/Resources/app/lib/backend/resources/arduino-cli'
EINK_CONFIG="$EINK_ROOT/.local/arduino-cli.yaml"
EINK_FQBN='esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,MSCOnBoot=default,DFUOnBoot=default,UploadMode=default,FlashMode=qio,FlashSize=16M,PartitionScheme=app3M_fat9M_16MB,PSRAM=opi,CPUFreq=240,LoopCore=1,EventsCore=1,DebugLevel=none,UploadSpeed=115200,EraseFlash=none'
```

설정 파일의 다음 경로는 실제 프로젝트 절대 경로로 작성합니다. 전역 기본 설정에 의존하지 않습니다.

```yaml
board_manager:
  additional_urls:
    - https://espressif.github.io/arduino-esp32/package_esp32_index.json
directories:
  data: /프로젝트/절대경로/.local/arduino/data
  downloads: /프로젝트/절대경로/.local/arduino/downloads
  user: /프로젝트/절대경로/.local/arduino/user
build_cache:
  path: /프로젝트/절대경로/.local/arduino/build-cache
updater:
  enable_notification: false
```

설치와 빌드 명령:

```sh
"$EINK_CLI" --config-file "$EINK_CONFIG" config dump
"$EINK_CLI" --config-file "$EINK_CONFIG" core update-index
"$EINK_CLI" --config-file "$EINK_CONFIG" core install esp32:esp32@2.0.17
git clone --branch esp32s3 https://github.com/Xinyuan-LilyGO/LilyGo-EPD47.git .local/libraries/LilyGo-EPD47
git -C .local/libraries/LilyGo-EPD47 checkout --detach 50224221fb81a8fcf9068532374b775af84a38d4
"$EINK_CLI" --config-file "$EINK_CONFIG" board details --fqbn esp32:esp32:esp32s3
"$EINK_CLI" --config-file "$EINK_CONFIG" compile \
  --fqbn "$EINK_FQBN" \
  --library "$EINK_ROOT/.local/libraries/LilyGo-EPD47" \
  --build-path "$EINK_ROOT/.local/build/first_image" \
  --warnings default firmware/first_image
```

## 백업과 복구

### 출고 펌웨어 보관

백업은 개별 기기의 데이터가 포함될 수 있으므로 외부 저장소에 올리지 않습니다.

- 파일: `artifacts/firmware-backups/factory-20260919.bin`
- 대상 범위: 주소 `0x0`부터 `0x1000000`바이트, 전체 16MB
- 크기: 16,777,216바이트
- SHA-256: `f0944ec95db31e8aa21a9cab0fdb08cc8a962b2f66f3d3733a88a3b8f95762f8`
- 원본 Flash 대조: 주소 0의 전체 16MB `verify_flash` 성공, `verify OK (digest matched)` 확인
- 보안 조회: Secure Boot와 Flash Encryption 모두 Disabled
- 첫 읽기 시도: 460800 설정에서 `The chip stopped responding`으로 실패, 백업 파일 미생성
- 5.1.0의 115200 재시도는 읽기가 진행되지만 느려 중단했습니다. 미완성 읽기를 유효한 백업으로 사용하지 않았습니다.
- 4.5.1의 `usb_reset`, 460800 설정으로 64KB 읽기를 확인했습니다. 관측된 전송은 약 71kbit/s로 설정한 baud 수치와 달랐습니다.
- 실제 백업 방법: 1MB 구간 16개를 0xFF 파일과 MD5 대조하고, 비어 있지 않은 두 구간은 다시 64KB 단위로 대조했습니다. 빈 것이 확인된 구간만 0xFF로 채우고 주소 `0x00000000`의 1,048,576바이트와 `0x00ff0000`의 65,536바이트를 실제로 읽어 16MB 파일을 구성합니다. 주소 0부터 전체 파일의 원본 Flash 대조가 성공해야 유효한 백업으로 인정합니다.
- 근거 로그: `flash-blank-map.log`, `flash-blank-map-fine.log`, `flash-read-00000000.log`, `flash-read-00ff0000.log`, `backup-verify.log`

조회한 현재 포트를 사용합니다. 백업 동안 원래 앱을 실행시키지 않도록 명령 종료 후 부트로더에 머뭅니다. 아래는 최적화 없이 전체를 직접 읽는 재현 명령이며, 위 구간 대조 방식보다 오래 걸립니다. 실제 실행에서는 모든 비교의 Flash 매개변수를 `keep`으로 지정했습니다.

```sh
EINK_ESPTOOL="$EINK_ROOT/.local/arduino/data/packages/esp32/tools/esptool_py/4.5.1/esptool"
EINK_PORT='<현재 다시 조회한 대상 포트>'
"$EINK_ESPTOOL" --chip esp32s3 --port "$EINK_PORT" --baud 460800 --before usb_reset --after no_reset_stub \
  read_flash 0 0x1000000 artifacts/firmware-backups/factory-20260919.bin
"$EINK_ESPTOOL" --chip esp32s3 --port "$EINK_PORT" --baud 460800 --before usb_reset --after no_reset_stub \
  verify_flash --diff no --flash_mode keep --flash_freq keep --flash_size keep \
  0 artifacts/firmware-backups/factory-20260919.bin
shasum -a 256 artifacts/firmware-backups/factory-20260919.bin
```

### 복구 절차

복구 명령은 원래 펌웨어로 돌아갈 때만 실행합니다. 이번 검증 중 실제 복원 시험은 별도로 표시하지 않는 한 수행하지 않은 상태입니다.

1. 현재 연결을 다시 조회하고 백업을 뜬 대상 보드와 일치하는지 확인합니다.
2. 백업 크기 16,777,216바이트 및 기록된 SHA-256을 확인합니다. `factory-20260919.sha256` 파일도 함께 보관합니다.
3. 보드가 자동으로 연결되지 않으면 BOOT를 누른 채 RST를 눌렀다가 RST, BOOT 순서로 놓아 다운로드 모드에 진입합니다.
4. 전체 백업을 주소 0에 쓰고 원본 파일과 대조합니다. 마지막에 정상 부팅시키고 실제 출고 화면을 확인합니다.

```sh
"$EINK_ESPTOOL" --chip esp32s3 --port "$EINK_PORT" --baud 115200 --before usb_reset --after no_reset_stub \
  write_flash --flash_mode keep --flash_freq keep --flash_size keep \
  0 artifacts/firmware-backups/factory-20260919.bin
"$EINK_ESPTOOL" --chip esp32s3 --port "$EINK_PORT" --baud 115200 --before usb_reset --after hard_reset \
  verify_flash --diff no --flash_mode keep --flash_freq keep --flash_size keep \
  0 artifacts/firmware-backups/factory-20260919.bin
```

## 시험 펌웨어와 판정

`firmware/first_image/first_image.ino`는 공식 `drawImages`를 바탕으로 작성했습니다. 이미지 헤더 3개는 원본과 동일하며 스케치 머리말에 출처·저작권·커밋과 변경 내역을 기록했습니다. 원본 저장소의 라이선스는 [GPL v3](https://github.com/Xinyuan-LilyGO/LilyGo-EPD47/blob/50224221fb81a8fcf9068532374b775af84a38d4/LICENSE)입니다.

- 패널: 960×540, 4비트 16계조
- 표시: 첫 이미지 원본 영역, 둘째·셋째는 전체 화면 버퍼에 복사
- 둘째 이미지: 원본이 960×576이며 공식 복사 함수가 패널 높이 540으로 잘라냄
- 프레임 버퍼: PSRAM에서 259,200바이트 할당
- 출력 횟수: 부팅당 3장, 각 그림 전 전체 지우기, 그림 출력 후 패널 전원 끄기·3초 대기
- 완료 후: 마지막 화면 유지, 화면 갱신 없이 대기
- 시간 로그: 전체 지우기 호출과 그리기 호출을 분리; 실제 패널 변화 속도나 게임 FPS를 뜻하지 않음

| 검증 | 결과 |
| --- | --- |
| 원본 이미지 파일 비교 | 3개 모두 SHA-256 일치 |
| 최소 예제 빌드 | 성공, 프로그램 1,008,113바이트 / 전역 변수 19,424바이트 |
| Flash 백업·대조 | 전체 16MB 파일 생성, 원본 Flash MD5 대조 통과, SHA-256 기록 |
| 시험 펌웨어 업로드 | 성공, 부트로더·파티션·boot_app0·앱 4개 쓰기 모두 해시 검증 통과 |
| PSRAM 런타임 조회·할당 | API 조회 8,386,295바이트, 259,200바이트 버퍼 할당 성공 |
| 종료 로그 및 반복 중단 | FIRST_IMAGE_DONE images=3 panel_power=off updates=stopped 확인 |
| 실제 이미지 출력 | 2026-09-19 18:13 KST 사용자 확인: “어 잘 나오고 있음” |
| 잔상·장시간 안정성 | 미측정 |

제조사 예제 문서에 재부팅 가능성에 관한 주의가 남아 있으므로 시작 로그 반복·크래시가 관측되면 정상 완료로 판정하지 않습니다. 무한 반복 시험은 수행하지 않습니다.

빌드에는 코어 2.0.17과 공식 드라이버만 필요했으며 SensorLib·Button2·ArduinoJson은 설치하지 않았습니다. 제조사 `epd_draw_oval()`에서 `round` 선언 관련 경고가 발생했으나 이번 시험에서 해당 도형 함수는 호출하지 않으며 제조사 코드는 수정하지 않았습니다.

시험 앱 바이너리 `.local/build/first_image/first_image.ino.bin`은 1,008,480바이트이며 SHA-256은 `159192470164a34a18b0baed88e0e41a3891ec7771f07975ac2647d7c13ebd08`입니다.

### 업로드와 장치 로그

2026-09-19 18:03 KST에 백업 대상과 업로드 장치의 식별자가 일치함을 다시 확인하고 업로드했습니다. 원본 로그는 `artifacts/logs/upload.log`, `runtime.log`에 보관합니다. 포트 이름은 다시 조회한 값을 사용했습니다.

```sh
"$EINK_CLI" --config-file "$EINK_CONFIG" board list
# 출력에서 현재 대상 장치를 확인한 뒤 EINK_PORT를 지정한다.
"$EINK_CLI" --config-file "$EINK_CONFIG" upload \
  --fqbn "$EINK_FQBN" --port "$EINK_PORT" \
  --input-dir "$EINK_ROOT/.local/build/first_image" \
  --verify firmware/first_image
```

Flash 런타임 조회는 16,777,216바이트였습니다. PSRAM의 물리 용량은 칩 조회상 8MB이고 Arduino의 사용 가능한 PSRAM API 조회값은 8,386,295바이트입니다. 버퍼 할당 후 여유 PSRAM은 8,127,079바이트였습니다.

표시 조건은 공식 드라이버 `50224221...`, ESP32 코어 2.0.17, 4비트 회색조, 그림별 전체 지우기 1회입니다. 아래 시간은 펌웨어의 `millis()` 차이로 측정한 함수 호출 시간입니다.

| 이미지 | 표시 영역 | 전체 지우기 호출 | 그리기 호출 | 출력 후 대기 |
| --- | --- | --- | --- | --- |
| 1 | 721×540, 좌상단 | 1,355ms | 601ms | 3초 |
| 2 | 960×540 | 1,355ms | 610ms | 3초 |
| 3 | 960×540 | 1,355ms | 610ms | 3초 |

3장 출력·대기의 합은 약 14.9초이며, USB 연결 대기와 초기화 시간은 별도입니다. 실제 화면 전환 속도·입력 지연·연속 부분 갱신 성능은 측정하지 않았습니다. 게임에 필요한 10~12fps 달성 여부를 이 결과로 판단하지 않습니다.

업로드 직후 40초간 직렬 출력을 수집했습니다. 시작 1회, 이미지 시작·완료 각 3회, 전체 종료 1회였고 오류·재부팅을 나타내는 추가 시작 로그는 없었습니다. 이후 직렬 포트를 닫았습니다. 전원을 다시 넣거나 RST를 누르면 부팅당 3장 시험이 다시 실행됩니다.

실물 확인: 마지막 캐릭터 그림의 표시와 유지 여부를 요청했고 사용자는 “어 잘 나오고 있음”으로 응답했습니다. 이를 실제 이미지 출력 확인으로 기록하며, 잔상이나 장시간 깜빡임에 대한 별도 측정값으로 해석하지 않습니다. 원본 이미지 방향을 유지하므로 가로 화면 기준 캐릭터가 옆으로 누워 보이는 것은 원본 배치입니다.

실행 후 전역 ESP32 코어 3.3.7과 SDLPoP의 `src/common.h` 수정 한 줄이 그대로임을 확인했습니다. 이번 작업에서 제조사 드라이버 소스도 변경하지 않았습니다.

## 완료 범위와 후속 판단

출고 펌웨어 복구 수단 확보부터 공식 정적 이미지의 실제 출력까지 첫 계획의 성공 조건을 충족했습니다. 백업 복원 자체는 실행하지 않았습니다. 다음에는 별도 계획과 승인 범위에서 횟수·시간을 제한한 흑백 애니메이션을 시험하고, 갱신 호출 시간과 실물 움직임·잔상을 구분해 측정할 수 있습니다. USB 전송·SDLPoP 연동과 장시간 부분 갱신은 이번 완료 범위에 포함하지 않습니다.
