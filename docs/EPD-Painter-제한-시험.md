# EPD_Painter H716 제한 시험

2026-09-27. 사용자 “계속 진행”에 따라 [호환성 조사](고속-드라이버-호환성-검토.md)의 후속 어댑터를 구현했다. 현재 호스트 검증과 ESP32 빌드를 통과했으며, 실물 표시 속도와 화질은 아직 측정하지 않았다.

## 고정 조건과 변경

- 실물: Screen-4.7-S3 V2.4 / 2024-12-03, ESP32-S3 240MHz, Flash 16MB, PSRAM 8MB.
- 정본: `repos/EPD_Painter`, 브랜치 `codex/eink-pop-bounded-test`, 원본 `6335a149c5a9b3be4150880e0be64ef2529ba62a` → 수정 `7544e2da178fb7be99620ba94d32bb921155ad3a`.
- `EPD_LILYGO_EPD47_H716_PRESET` 설정 객체를 생성자에 명시한다. 전용 프리셋 전처리 매크로의 기존 빌드 오류는 이번에 수정하지 않았다. 기본 AUTO가 컴파일돼도 명시적 핀 설정으로 탐색 전에 반환한다.
- FAST 4명도, 960×540, 작성자가 제공한 H716 파형·타이밍 그대로다. DMA 주사 루프·파형·핀맵은 수정하지 않았다. direct trains 기능을 추가로 활성화하지 않았다.
- `setAutoShutdown(false)`로 현재 충전 회로와 맞지 않는 BootCtl을 사용하지 않는다. 전체 C++ 빌드에 `EPD_PAINTER_NO_NVS`를 지정해 저장된 조정값의 개입을 차단한다.
- 기본 5초 idle 전원 타이머는 60초로 늘리고, 정상 시험 끝에는 명시적으로 패널 전원을 끈다. 타이머만으로 시험 종료를 판정하지 않는다.

`paintIdle()`/`paintStage==0`은 두 번째 전이가 끝나기 전에 성립할 수 있다. 새 `waitForIdle(timeout_ms)`는 stage와 출력 세마포어, 마지막 LCD 전송 종료를 함께 검사한다. `powerOffWhenIdle(timeout_ms)`는 같은 전체 제한시간 안에서 완료 대기 후 기존 idle 전원 잠금을 얻어 OFF를 호출하고 카운터를 0으로 만든다. **초기화 성공 후 한 호출자만 제출하는 조건**의 API다. 전원OFF 반환은 레일 전압을 계측했다는 의미가 아니다.

초기화에는 GDMA·버퍼·세마포어·출력 태스크 생성 실패 검사를 추가했다. 일부 할당 실패의 완전한 자원 회수나 재초기화를 구현한 것은 아니다. 이 시험은 부팅당 한 번만 실행하며 begin 실패 시 재시도하지 않는다.

## 시험 앱 동작

정본 스케치: `firmware/painter_bounded/painter_bounded.ino`.

1. 부팅 시 USB READY만 출력한다. 유효한 시작 명령 전에는 `begin()`도 호출하지 않는다.
2. `STILL\n`은 정지 패턴 한 장, `MOVE\n`은 이동 도형 12장이다. 시작 명령은 한 번만 받으며 잘못된 명령·초과 길이·비정상 바이트·뒤에 쌓인 추가 명령은 오류로 끝낸다.
3. 초기 버퍼를 흰색으로 맞추고 전체 정리 한 번을 수행한다. STILL은 왼쪽부터 흰색·밝은 회색·어두운 회색·검정 100×100 상자와 아래 검은 선이다. 점무늬가 없는 실제 4명도 입력이다.
4. MOVE는 흰 배경의 64×64 검은 사각형을 x=200부터 16픽셀씩 오른쪽으로 옮긴다. 프레임 사이 100ms를 쉬고 최대 12장에서 끝낸다. 이번 최초 관찰에서는 실행하지 않는다.
5. 시작 후 30초를 넘기면 추가 프레임 제출을 중단한다. 완료 대기·전원 잠금은 5초 한도다. `begin/clear/paint` 내부가 막히면 이 검사까지 도달하지 못하므로, 실물 시작 도구의 별도 45초 한도와 다운로드 모드 중단이 필요하다. 엄밀한 30초 강제 중단 보장은 아니다.
6. 출력 중 새 직렬 입력은 다음 프레임 경계에서 중단 요청으로 처리한다. 완료 후에는 전원을 끄고 마지막 그림을 남긴다. 추가 START나 프레임은 처리하지 않는다. OFF 실패 시 정상 DONE을 출력하지 않는다.

`PAINTER_FRAME display_us`는 입력 제출부터 실제 주사 완료 대기까지의 소프트웨어 시간이다. 마지막 중립 주사도 포함하며, 광학 명암 안정 시간·실제 보이는 fps와 구분한다. `cycles`는 드라이버의 완료 카운터 차이로 1~2만 허용한다.

## 첫 시작 중단과 메모리 검사 수정

2026-09-27 23:26 KST, 사용자 “준비됨” 후 `STILL`을 한 번 보냈다. 앱은 `PAINTER_ERROR reason=board_config`를 반환했다. START/CLEAR/FRAME/DONE은 모두 0회이고, 패널 초기화 전 검사에서 종료됐다. 호스트는 다운로드 모드 전환에 성공했고 직렬 포트를 닫았다. 원본 `artifacts/painter-bounded-20260927/still-{runtime.log,result.json,stop.log}`을 보존한다. 화면 출력 성공이나 새 드라이버의 실물 구동 실패로 해석하지 않는다.

원인은 시험 앱이 `ESP.getPsramSize()`를 물리 8MiB와 비교한 것이다. 현재 Arduino 2.0.17의 `cores/esp32/Esp.cpp` 구현은 `heap_caps_get_info()`의 free+allocated 바이트를 반환한다. 힙 관리 공간을 제외하므로 정상 보드에서도 8MiB보다 작다. 과거 정상 실행 로그에서도 8386279/8386295바이트를 확인했다. 첫 오류 로그는 CPU/PSRAM을 구분하지 않았으므로 이번 호출의 수치는 직접 기록되지 않았다.

v2는 `psramFound()` 확인 후 SDK `esp_spiram_get_size()`로 물리 용량을 검사하고, READY에 CPU MHz·물리 PSRAM·힙 크기를 각각 기록한다. 패널 초기화 없이 검사 원인을 확인할 수 있다. 힙 반환값을 실제 기록값 8386279로 바꾼 native 검증과 PSRAM 미인식 사례를 포함해 21개 사례가 통과했다. 메모리 용량 부족·미인식은 계속 거부하며, 실제 캔버스 할당 실패 검사도 유지한다. 드라이버 파형·완료 API는 변경하지 않았다.

### 사용자 관찰과 남은 잔상

사용자는 “다 보여. 지금 화면은 멈춰있고. 그런데 뒤에 흐릿하게 예전 pop 화면이 남아있네”라고 확인했다. 패턴 표시와 정지는 확인했지만 배경의 과거 게임 화면 잔상은 남았다. 새 패턴 자체의 연속 이동 잔상을 측정한 것은 아니다.

이번에는 지우기를 생략하지 않았다. 스케치가 `panel.clear()`를 한 번 호출했고, 기본값은 전체 영역 `ClearMode::HARD`다. 소스는 4개 극성 단계에 6·2·4·8회씩 전체 행을 주사하고 중립 주사로 마친다. 실제 호출과 완료 대기 합계는 223.417ms였다. 이름이 HARD라는 사실만으로 광학적으로 완전히 지워졌다고 판단할 수 없으며 사용자 관찰이 그 한계를 보여준다.

제조사 `epd_clear()`는 별도의 4회 흑/백 묶음(각 묶음당 흑 4회·백 4회, cycle_time=50)을 사용한다. 단순 주사 횟수만으로 각 방식의 물리 구동량이나 잔상 제거 성능을 동등 비교할 수 없다. 과거에는 제조사 전체 정리 한 번으로 사각형 잔상이 완전히 사라진 사용자 확인이 있다. 따라서 이번 과거 게임 흔적은 새 드라이버의 초기 정리가 충분하지 않았을 가능성을 먼저 검증해야 하며, 현재 관찰만으로 패널 불량·영구 손상으로 판정하지 않는다.

다음 이동 시험 전에 깨끗한 배경 기준을 확보할 필요가 있다. 검증된 제조사 정리와 새 드라이버 초기 정리를 구분해 비교하고, 기존 잔상이 제거된 상태에서 새 시험이 만드는 잔상을 관찰해야 한다. 이번 응답에서는 추가 지우기·재부팅·MOVE·파형 조정을 실행하지 않았다.


## 제조사 정리로 기준 확보 후 첫 이동 시험

사용자 “다음 진행…특별히 내가 얘기하지 않아도 계속 진행”에 따라 구현·업로드 준비마다 승인을 반복하지 않고 실물 관찰만 요청했다. [후속 계획](../.Codex/plans/PLAN-20260927-2335-clean-baseline-painter-move.md)에 범위와 결과를 기록한다.

### 이전 잔상 제거

동일 장치·백업·앱 해시를 확인하고 기존 제조사 콜백 앱 `9b8dcdb` / SHA-256 `14e2283dd41b8fcfcb3e35021bc3fd3409e98525f37baf3a553b88f370960c48`을 한 번 업로드했다. Flash 4구간 검증 뒤 기존 호스트 `host/usb_frame.py`로 전체 흰색 320×200 한 장을 전송했다. 흰색 payload 8000바이트는 전부 0이며, 실제 송신 8049바이트가 START 1장 제한+FRAME 1개와 완전히 같음을 재검증했다. ACK의 CRC·순서·완료를 확인했다.

- 전체 지우기 `clear_us=1324097`, 추가 그림 `white_us=0`, `black_us=0`.
- 표시 호출 전체 1325866µs, 최초 지연 검사 통과, ACK applied 1회, DONE limit/frames=1/applied=1.

- 사용자는 **“흔적이 모두 사라졌어요”**라고 확인했다. 과거 PoP와 정지 상자의 흔적은 제조사 정리 한 번으로 제거됐다. 이번 흔적을 영구 손상으로 볼 근거가 없으며, 새 드라이버의 초기 정리 효력 부족을 우선 문제로 기록한다.

원본은 `artifacts/painter-clean-baseline-20260927/`에 있다. 두 드라이버를 동시에 초기화하거나 새 파형을 조정하지 않았다.

조건은 드라이버 `7544e2d`, 앱 v2 SHA-256 `6e61fb81a86098889e69d73e574c8c3af7b96aeff7ad6b2346bdc260d3c74db5`, H716 FAST 4명도, 960×540 흰 배경, 64×64 검은 사각형, x=200부터 16픽셀씩 12장, y=240이다. 매 프레임 사이 100ms 대기가 있다. 표시 내용은 흑백 끝점 두 값뿐이며 회색조 게임 시험이 아니다. 초기 Painter 전체 정리는 223.415ms였다.

## 실제 게임 연속 12장 준비

게임 전체 입력 연결 전에, 이전에 정상 수집한 SDLPoP 데모의 프레임 40~51을 사용한다. 같은 방에서 인물이 왼쪽으로 달리고 틈을 뛰어넘는 연속 장면이며 원본 수집 시각 차이는 0.922883초다. Mac에서 게임을 새로 실행하거나 조작하지 않는다.

`host/prepare_painter_clip.py`는 기존 수집 검증기의 파일·SHA·번호 검사를 사용한 뒤 누락 없는 12장만 선택한다. 기존 중간톤·생명력 보정을 적용하고 가장 가까운 4명도로 양자화한다. 2bpp에서 흰색=0·검정=3, 바이트 안에는 왼쪽 픽셀부터 상위 2비트다. 점무늬를 새로 만들지 않지만 원래 게임의 벽돌 질감은 남는다. 생명력 밝은 빨강은 흰색, 어두운 빨강은 밝은 회색으로 변환한다.

```sh
python3 host/prepare_painter_clip.py --capture artifacts/scene-comparison-20260927/demo/frames --output artifacts/painter-game-20260927/clip --start-sequence 40
python3 tests/test_painter_clip.py
python3 tests/test_painter_bounded.py
```

선택적 `EINK_PAINTER_GAME` 빌드만 생성 헤더 `painter_game_frames.h`를 포함하고 GAME 명령을 받는다. 일반 빌드의 STILL/MOVE는 그대로다. 게임 12장의 192000바이트를 Flash에 미리 넣고 320×200을 중앙 640×400으로 2배 확대한다. USB는 시작·관찰용이며 게임 프레임 실시간 전송 속도는 측정하지 않는다. GAME에는 도형 시험의 100ms 대기가 없고, 나머지 부팅당 한 번·30초 한도·완료/전원OFF·오류 중단은 유지된다.

검증: 변환 7개 테스트, 기본/게임 빌드의 실제 스케치 44사례(ASan/UBSan)가 통과했다. 4명도 값·생명력 경계·2bpp 비트 순서·연속/손상 입력·헤더 바이트·클립 해시를 확인했고, 실제 C++ 확대 결과의 960×540 전체 픽셀과 GAME에서 100ms 대기 없음도 검증했다. 미리보기 6장을 확인해 인물·벽돌·생명력과 이동/점프가 구분됨을 확인했다. 이것은 보드의 광학 평가가 아니다.

- 클립 SHA-256: `77a0c506cc07bf465391de329b8ace8a002746be4c16ccb8e9c07d9dd8d03624`.
- 드라이버: 변경 없이 `7544e2d`. 코어 2.0.17/C++17/NVS 비활성화, 추가 플래그 `-DEINK_PAINTER_GAME -I<생성 헤더 디렉터리>`.
- 앱 523664바이트, SHA-256 `408396075844eede5b13ec5dbbbde79875bf2bbf9772faf282e5c73a3cb81dca`. 부트로더/파티션 해시는 이전과 같다.
- 앱 내부에 클립 192000바이트가 한 번 정확히 포함돼 있고 READY의 클립 식별자도 포함됨을 검증했다.
- 앱 빌드 보고: 프로그램 523241바이트, 정적 전역 25848바이트. `.local/build/painter_game`과 `artifacts/painter-game-20260927/{build-verification.json,clip/manifest.json,preview.png}`에 근거를 남겼다.

이전 이동 경로 잔상은 제조사 지우기 한 번을 거친 후 게임 표시를 진행한다. 이번 정리의 로그 성공과 광학적으로 완전한 흰색이 됐는지는 구분하며, 같은 정리의 제거 효력은 직전 사용자 확인을 근거로 한다. 실제 게임 12장 시험은 아직 시작하지 않았다.


### 실제 게임 12장 실행 결과

연속 진행 승인에 따라 직전 도형 잔상을 제조사 전체 지우기 한 번으로 정리했다. clear 1324155µs·추가 흑/백 그림 0회·한 장 정상 종료와 이후 10초 무응답을 확인했다. 이번 정리 직후의 광학 상태를 다시 묻지는 않았고, 앞선 동일 방식의 제거 확인과 구분한다. 원본은 `artifacts/painter-game-clean-20260927/`이다.

게임 앱을 한 번 업로드해 Flash 해시 4개와 v3 READY 9회/8.009471초를 확인했다. CPU 240MHz·PSRAM 8MiB·클립 식별자 `77a0c506cc07bf46` 일치, 준비 시 START 0회였다. 이후 15초 관찰 예고 후 GAME 한 번만 실행했다.

이번 약7.35장/초는 Flash의 녹화 프레임을 재생한 소프트웨어 완료 간격이다. 광학 fps·실시간 입력 지연이나 서로 다른 원본으로 시험했던 제조사 게임 결과 대비 정확한 개선 배율은 아니다. 실제 게임 로직의 약12fps와 동일 속도로 표시됐다고 볼 수도 없다. 원본·구동 프로파일·분석은 `artifacts/painter-game-20260927/{game-runtime.log,game-result.json,timing-summary.json}`에 보존했다. 사용자 움직임·가독성·잔상 관찰은 대기 중이다.

후속 코드 조사에서는 H716 FAST에 회색 간 직접 전이 표 6개가 있음을 재확인했다. 기존 두 주기 대신 한 번에 구동할 수 있는 후보지만 표 길이가 3~12주사로 다르고, 한 주기로 바꾼다고 시간을 절반으로 줄인다는 뜻은 아니다. 이번 앱에서는 활성화하지 않았으며 광학·전하 균형·표 적용 조건을 검토하기 전 실제 시험하지 않는다.
