## 목표와 판정

기존 개발 인계의 표시 목표는 10~12장/초다. 이번 최소 목표는 **변경된 게임 화면의 실제 완료 응답 간격 평균 100ms 이하(10장/초 이상), p95 125ms 이하**다. 목표를 현재 성능에 맞춰 낮추지 않는다.

- 640×400 게임 영역, 320×200 원본, NORMAL 4명도 기준으로 비교한다. 화질·해상도를 낮춘 후보는 별도 결과이며 같은 목표를 달성했다고 처리하지 않는다.
- 완료 간격은 호스트의 단조 시계 ACK 수신 시각 차이다. 처음 전체 정리/초기화는 정상 구간 평균에서 제외하고 별도로 보고한다. 각 12장 시험의 11개 간격에서 p95는 nearest-rank 방식으로 산출한다.
- 정지 화면 반복이나 미구동 ACK로 속도를 부풀리지 않는다. 전송 원본·CRC·실제 변경·드라이버 완료 주기를 검증하고, 무변경 표본이 있으면 분리 보고한다.
- 목표 후보는 이동·점프·전투를 포함하는 고정 입력으로 비교하고, 최신 프레임 선택 경로에서도 측정한다. 녹화 재생·호스트 단독 벤치마크만으로 실시간 목표 달성을 선언하지 않는다.
- ACK 속도는 광학 fps나 버튼 입력 지연이 아니다. 원본 프레임 선택 간격, 수신/준비/paint 시간, 프레임 읽기~ACK 시간도 함께 기록한다.
- 사용자 확인 없이 가능한 것은 동일 입력/출력·구동 조건을 보존하는 최적화다. 파형·주사 간격·전압을 바꾸면 이전의 “잔상 없음” 평가를 승계할 수 없다. 광학 미검증 후보로 구분하고 사용자 확인을 매 회 요구하지 않는다.

## 종료 조건

1. 위 성능 목표와 검증 조건을 충족하면 목표 달성으로 종료한다.
2. **조회 가능한 Codex 한도 중 하나라도 잔여량이 50% 미만이면 개선 반복을 중단한다.** `remaining = 100 - usedPercent`. 정확히 50%는 사용자 조건상 중단 경계 미만이 아니다. 미제공 한도를 0% 또는 충분한 잔여량으로 가정하지 않는다.
3. 사용자 중단 요청, 장치 오류, 복구/전원 종료 확인 실패가 있으면 즉시 해당 실행을 중단한다. 목표 미달을 성공으로 바꾸지 않는다.
4. 사용량 조회가 실패하면 새 비용 큰 회차·업로드를 시작하지 않고 재조회한다. 확인 없이 계속 진행하지 않는다. 리셋 크레딧은 사용하지 않는다.

한도는 매 회 시작/종료 및 긴 회차의 빌드·업로드·실측 경계마다 조회한다. 조회 사이의 사용량 변화를 완전히 실시간 감시할 수는 없다. 중단 조건 도달 시 진행 중 장치를 정상 종료하고 결과·복구 상태·다음 작업을 저장하는 정리만 수행한다.

2. 아래에 회차 번호, 목표, 병목 근거, 변경 대상, 검증 방법, 채택/기각 기준, 시작 사용량을 **실행 전에** 추가한다.
3. 작은 변경을 구현하고 관련 검증을 실행한다. 의미 있는 새 후보만 장치에서 최대12장·30초로 측정하고 매 시험 종료/전원 OFF/10초 무출력을 확인한다. 실패한 시험을 그대로 무한 재시도하지 않는다.
4. 종료 기록에 결과물 경로·수치·테스트·한계·채택/기각·종료 사용량·다음 작업을 쓴다. 현재 상태 표도 갱신한다.
5. 관련 변경은 하위 저장소부터 로컬 커밋하고 상위 참조를 갱신한다. **push하지 않는다.** 기록 파일 자신을 포함한 커밋은 Git 이력으로 조회하며 자기 커밋 해시를 문서에 다시 쓰는 순환 커밋은 만들지 않는다.
6. 종료 조건을 다시 판정하고, 미충족이면 다음 회차 시작 기록을 작성한다. 새 작업 시작 여부를 매번 사용자에게 묻지 않는다.

## 개선 우선순위와 알려진 한계

1. 호스트 픽셀 변환: 같은 색 반복 계산을 줄인다. Python 단일 프레임 사전 측정에서 19.155→6.847ms 후보가 나왔지만 단일 입력만 확인했으므로 아직 채택 전이다.
2. 보드 수신·CRC·확대 준비: 현재 수신 평균38.462ms, 준비6.842ms. 픽셀·패킷·오류 처리를 유지하면서 줄일 수 있는지 측정한다.
3. 전송과 구동의 겹침: 호스트→보드 대기 비용을 줄일 수 있으나 오래된 프레임 큐와 추가 버퍼 수명 문제가 생길 수 있다. 먼저 시간 분해 후 필요성을 판단한다.
4. 드라이버 내부: 현재 NORMAL 직접 전이는 특정 회색 전이에서19주사이며 주사 간 대기만76ms다. 전체 paint 약189~204ms가 큰 병목이다. 이 조건에서 호스트 최적화만으로10Hz를 달성할 수 없음을 명시한다.
5. 주사 속도·파형 변경: 패널의 유효 구동량까지 바꿀 수 있으므로 일반 CPU 최적화와 구분한다. 전압/주사 상한·광학 근거 없이 대기만 삭제해서 목표를 달성했다고 주장하지 않는다.

## 회차 2 — 보드 수신·확대 준비 최적화와 동일 입력 실측

### 시작 기록

- 상태: 실행 중. 기준58496f7. 시작 사용량은 최근 조회 주간 잔여60%; 장치 실행 경계에서 재조회한다.
- 목표: 파형과 픽셀을 유지하면서 CRC 계산과 PSRAM 확대 쓰기 비용을 줄인다. 같은12장 입력·같은 호스트로 이전/새 펌웨어를 비교한다.
