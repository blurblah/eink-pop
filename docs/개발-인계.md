## 4. 화면 전송 구성

```text
Mac 키보드 → SDLPoP → 최종 화면 추출·흑백 변환 → USB
                                                    ↓
                                      ESP32 수신·확대·화면 갱신
                                                    ↓
                                                e-paper
```

USB 수신 펌웨어와 SDLPoP 화면 전송 코드는 아직 없습니다. USB-C 연결은 범용 모니터 입력 기능을 뜻하지 않습니다. ESP32에서 SDLPoP를 그대로 `make`할 수도 없으며, 단독 실행에는 별도 이식이 필요합니다.

원본 320×200 화면을 흑백 1비트로 보내면 한 프레임은 8,000바이트입니다. 12프레임/초의 순수 픽셀 데이터는 계산상 96,000바이트/초이며, 프로토콜 오버헤드는 별도입니다. 확대를 ESP32에서 처리하는 구상을 검토했습니다. 이는 실측 전송 속도나 화면 성능이 아닙니다.

후속 구현에서는 패널 처리가 게임 입력을 막지 않도록 전송과 갱신을 분리하고, 밀린 프레임을 계속 쌓지 않는 방식이 필요합니다. 이 역시 아직 구현·검증 전입니다.

## 5. 표시 비율과 성능 기준

| 표시 방식 | 표시 영역 | 특징 |
| --- | --- | --- |
| 초기 검증 후보 | 640×400 | 원본 320×200을 가로·세로 2배 확대, 균일한 픽셀 |
| 원래 표시 비율 보정 후보 | 720×540 | 4:3, 좌우 각 120픽셀 여백. 비정수 확대이므로 픽셀 균일성에 타협 |
| 여백을 더 두는 비율 보정 | 640×480 | 4:3, 화면 안에 충분히 들어감. 세로는 비정수 확대 |

320×200은 데이터 해상도이고, 원래 CRT에서 의도한 표시 비율은 4:3입니다. 960×540 패널에는 3배 정수 확대인 960×600이 들어가지 않습니다. 어떤 방식을 쓸지는 실물 비교 후 정합니다.

SDLPoP 기본 시간 설정은 일반 동작 약 12fps, 전투 약 10fps입니다. 이것은 패널 성능이 아닙니다. 게임 적합성의 참고 목표는 실제 표시되는 동작이 10~12fps 수준에서도 구분되는지, 입력 지연·잔상·깜빡임이 플레이를 방해하지 않는지입니다. 목표 달성은 아직 보장하지 않습니다.

## 6. 드라이버와 확인되지 않은 한계

- 공식 `LilyGo-EPD47`의 `esp32s3` 브랜치를 기준으로 조사했습니다. 동일 이름의 구형 ESP32 보드, T5 Pro, 다른 EPD 라이브러리 지원 사례를 현재 보드에 그대로 적용하지 않습니다.
- 첫 출력 후보는 `drawImages`입니다. 그림 3장을 전체 지우기 → 출력 → 패널 전원 끄기 → 3초 대기로 반복합니다. 무한 반복과 딥슬립 없음에 유의하고 첫 검증은 몇 장만 확인하는 짧은 시험으로 제한합니다.
- 공식 `spi_driver`는 외부 Raspberry Pi에서 이미지를 받는 예제입니다. 수신 이미지마다 영역 지우기와 회색조 그리기를 수행하므로 그대로 게임용 속도를 보장하지 않습니다. 이번 첫 단계에서는 SPI 배선을 하지 않습니다.
- 판매 페이지는 장시간 부분 갱신 시 잔상과 복구 불가 손상 가능성을 경고합니다. 전체 정리 갱신을 특정 간격으로 넣으면 장시간 게임 사용이 안전해진다는 검증 자료는 확보하지 못했습니다.
- USB로 글자를 주고받거나 드라이버 함수가 빨리 반환되는 것만으로 실제 패널 갱신 속도를 판정하지 않습니다.

## 7. 후속 단계로 남긴 결정

- Pi Zero 2 W 구매와 독립형 기기 구성은 화면 성능 검증 후 결정합니다.
- 배터리·스피커·앰프·케이스·별도 버튼은 함께 설계할 후속 항목입니다.
- 보드의 배터리 충전 회로만으로 Pi에 5V를 공급하는 구성은 안 됩니다. 제조사 안내상 3.3V 확장 출력은 100mA 이하 부하이며 Pi 급전용이 아닙니다.
- 가로로 긴 화면과 하단 버튼을 결합하면 케이스가 커질 수 있다는 제품 기획상 우려가 있습니다.
