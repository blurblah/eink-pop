# USB 화면 전송과 SDLPoP 검증

실행일: 2026-09-20, Asia/Seoul. 사용자 승인: 실제 게임 화면 한 장 → 제한 연속 전송 설명 뒤 “진행해”.

## 현재 판정

정지 16계조 화면에서 밝기와 생명력 표시가 적당하다는 사용자 확인을 마쳤다. 후속 “진행” 승인으로 같은 변환을 실행 중 게임의 최신 PPM에 적용하는 USB v2를 구현했다. 호스트 27개·펌웨어 40개 검증과 ESP32-S3 빌드를 통과했으며, 보드 업로드·READY 확인을 마쳤고 실제 게임을 1레벨 시작에서 대기시켰다. 첫 실제 게임 시도는 1장 처리 후 USB 응답 지연·RX 시간초과로 중단했고, 통신 보완 중이다. 아래 v1 정지 화면의 측정은 당시 방식의 이력이다.

## 구성과 표시

```text
SDLPoP 최종 320×200 RGB 화면
  → 비차단 최신 슬롯 → 작업 스레드의 PPM 원자 교체
  → Python 호스트의 밝기·생명력 보정 → USB 32,024바이트 4bpp 패킷
  → ESP32 검증 → 640×400 확대·전체 지우기 후 16계조 출력 → ACK
```

선택적 환경 변수 `SDLPOP_EINK_FRAME_PATH`가 없으면 추출 기능을 사용하지 않는다. 게임 렌더링 스레드는 잠금이 즉시 가능할 때만 프레임을 복사하고, 파일 쓰기는 작업 스레드에서 한다. 화면 전송기는 처리 완료 ACK 뒤 최신 파일을 다시 읽는다. 게임 프레임을 모두 패널에 보여 주는 방식이 아니며 게임 입력·오디오는 Mac에 남는다.

프로토콜의 바이트·CRC·응답·중단 조건은 [USB 화면 계약 v2](USB-화면-프로토콜.md)에 기록했다. 입력은 4bpp 32,000바이트, 0=검정·15=흰색, 짝수 x 하위 nibble이다. 중간 회색을 한 단계 밝게 하고 기본 생명력 두 빨간색을 15/12로 우선 매핑한다. ESP32는 x=160,y=70에서 픽셀당 2×2로 확대한다. 4:3 비율 보정과 디더링은 하지 않는다.

제조사 grayscale API의 흰 바탕 전제에 따라 변경 화면마다 전체 지우기 후 회색조를 그린다. 무변경은 전원을 켜지 않는다. 버퍼는 960×400이며 좌우 흰 여백을 포함한다. 새 파형이나 교차 갱신 API는 사용하지 않는다. 현재 영역 지우기는 마지막 행의 펄스 경로가 전체 지우기와 달라질 수 있어 첫 연동에서는 정지화면에서 검증한 전체 지우기를 유지한다. 매번 깜빡이고 기존 정지 측정상 한 장 약 1.9초가 걸린다.

## 실행 범위와 측정의 한계

- 한 부팅에 한 세션, 최대 1~12프레임. 첫 실물 시험은 1장이다.
- 부팅·START·20초 지연 검사에서는 패널을 건드리지 않는다. 첫 FRAME의 길이·CRC·순서·세션까지 유효해야 출력한다.
- 최초 패널 전원 켜기부터 30초가 지나면 새 갱신을 시작하지 않는다. 시작한 전체 지우기는 회색 그림·전원 끄기까지 마친다.
- ACK 뒤 최소 250ms 간격으로 다음 최신 프레임을 보낸다. 변화 없는 수신도 프레임 수에 포함한다.
- CRC·순서·할당·시간초과·재부팅 오류에 자동 재전송·재접속하지 않는다. 종료 뒤 10초 동안 추가 실행 로그를 확인한다.
- ACK는 드라이버 호출과 전원 끄기가 반환됐다는 뜻이다. 실제 패널 광학 전환 완료·게임 입력 지연·안전한 장시간 사용을 증명하지 않는다.
- 기존 드라이버의 `epd_draw_image()`는 내부 자원 실패를 호출자에게 반환하지 않고 대기할 수 있다. 호스트 ACK 제한시간은 이 호출을 강제 중단하지 못한다. 오류·정지 시 추가 프레임을 보내지 않고 기존 장치 중단 절차로 다운로드 모드에 두며, 불가능하면 USB를 분리한다.

## 환경·원본 보존

드라이버는 `f1607da`의 기존 API를 사용하며 파형을 바꾸지 않는다. Arduino CLI 1.5.1, 프로젝트 코어 2.0.17과 S3·16MB Flash·OPI PSRAM·240MHz 설정을 유지한다. 기존 전역 환경은 변경하지 않는다.

구현 착수 때 출고 백업 16,777,216바이트 및 `bw_delta`, `bw_interleaved` 앱의 SHA-256이 기존 기록과 일치함을 확인했다. 외부 SDLPoP와 `.local` 제조사 원본의 HEAD·브랜치·상태·diff·파일 해시도 이관 전 기록과 같았다. 현재 USB 조회는 원본과 같은 장치임을 확인했고 식별자는 제외된 로그에만 저장했다.

## 로컬 화면 확인

기존 SDLPoP의 자동 스크린샷 명령으로 1레벨 첫 화면을 얻었다. SDL dummy 영상·오디오 환경에서도 320×200 RGB PNG가 생성됐다. 이 기능은 성공 시에도 `quit(1)`을 호출하므로 종료 코드 대신 생성된 파일·크기·내용을 확인했다. 주요 벽돌·인물·횃불은 128 문턱값 흑백에서도 구분됐으며 어두운 부분의 세부는 일부 합쳐졌다. 이것은 Mac 이미지 검사이고 실제 패널 결과가 아니다.

자동 스크린샷은 다음 `update_screen()` 전에 종료하므로 추출 PPM에는 앞서 표시한 Loading 화면만 남았다. 스크린샷 기능의 캡처 시점과 새 표시 훅을 구분한다. 이어서 새 빌드의 실제 게임을 dummy 영상·오디오 환경에서 4초 실행해 연속 추출을 확인했다. 1초 간격으로 PPM sequence가 10, 22, 34, 46으로 진행했고 RGB 해시도 달라졌다. 마지막 PPM은 실제 1레벨 인물·횃불·벽돌·남은 시간 화면이었다. 이 프로세스에 SIGTERM을 보내자 SDL 종료 처리로 코드 0을 반환했고 임시 파일도 남지 않았다. 일반 강제 종료의 마지막 프레임 저장을 보장하는 결과는 아니다.

실물 첫 출력에는 이 연속 추출 경로에서 얻은 유효한 1레벨 PPM 한 장을 사용한다. 다음 제한 연속 시험에서 게임을 띄워 같은 파일이 계속 최신으로 교체되게 한다. 두 경우 모두 화면 전송 프로그램과 패널 수신 경로는 같다.

```sh
make -C repos/SDLPoP/src -j4
# 저장소 루트에서 실행하며 PNG는 제외된 screenshots/에 생성된다.
cd repos/SDLPoP
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy ./prince megahit 1 --screenshot mute
```

## 실행 기록

후속 구현·시험·빌드·업로드·실물 관찰 결과를 확인한 순서에 따라 아래에 기록한다. 각 문단의 실행 여부는 당시 상태이며 최신 판정은 문서 첫머리를 따른다.

SDLPoP 전체 빌드가 성공했고 신규 exporter 경고는 없었다. 기존 `seg000.c`와 `stb_vorbis.c` 경고는 이번 변경과 무관해 유지했다. 실제 SDL 스레드와 제품 모듈을 포함한 하네스 13개가 통과했다. 느린 반쪽 임시 파일 기록 중 기존 출력 보존, 잠금이 바쁜 경우 즉시 반환, 최신 슬롯 덮어쓰기, 마지막 pending flush, 비활성·잘못된 화면·open/write/close/rename 실패를 포함한다. 이 검증은 파일 지연이 렌더 스레드의 파일 I/O 대기로 전파되지 않는 것을 확인하며 메모리 복사·OS 스케줄링 비용이 0이라는 뜻은 아니다.

실제 USB 스케치를 포함한 네이티브 하네스 40개가 `-Wall -Wextra -Werror`와 ASan·UBSan으로 통과했다. 분할 수신·CRC/길이/세션/순서 오류, START/RX 시간초과, 큐·읽기·할당·CPU·지연 검사 실패, terminal 차단을 포함한다. 전체 400행과 2행·6행 변경 범위의 모든 마스크·패널 픽셀, x319·비트/바이트 경계, 메모리 가드, 무변경, 오류 후 기존 화면 보존, 30초 경계의 새 전원 켜기 차단을 확인했다. 이는 논리·메모리 검증이며 실제 USB 전기 신호·패널 파형 측정은 아니다.

Python 실제 전송 루프의 PTY 시험 24개도 통과했다. 짧은 write/EAGAIN, 분할 READY·ACK, 잘못된 session/seq/CRC, 오류·EOF·시간초과·재부팅, ACK 전 다음 프레임 금지, 대기 중 B/C 파일 교체 후 최신 C 선택, STOP 순서·종료 후 추가 응답 거부를 포함한다. 독립 검토에서 READY가 다음 read나 부분 줄로 남으면 ACCEPT 전에 오판할 수 있음을 찾아 허용 범위를 ACCEPT 전까지로 한정했다. 종료 후 STATS가 무시되던 경로도 거부하도록 보강했다.

호스트·생산 펌웨어의 CRC를 session `0x10203040` 공통 벡터로 대조했다. START(1장)는 `fd8fcbc5`, FRAME(seq1, 8,000바이트 0)은 `2907d090`, STOP(seq2)은 `b0471eb4`로 일치했다. 실제 게임 PPM을 제품 호스트의 미리보기 경로로 변환해 인물·횃불·벽돌·시간 표기를 확인했다. 첫 시험 원본의 sequence는 46, RGB PPM SHA-256은 `322cf921b76b6447d227a5cdc27bdedf78f51abef8c3a0d757d2d72c26eb385e`, 8,000바이트 흑백 SHA-256은 `07b08603fcdeff2dba8ea23216a51cf4e073ca68de454046ef997da4c739a0f5`다.

최종 Arduino 빌드의 프로그램은 281,229바이트, 전역 변수는 19,552바이트다. 앱 바이너리는 281,600바이트이며 SHA-256은 `dfc935d48f86e67f66fc57136c6a15ffb7cce97109cc95447b514f7b274d74a0`이다. 빌드와 네이티브 검증 스케치 SHA-256은 `63fb08d3293f0d2dab371babf202e6a09d0c04581d05cd41f166b0caf298cb0f`로 같다. 드라이버 컴파일 단위 22개가 모두 `repos/LilyGo-EPD47` 경로이며 기존 제조사 `round` 경고 외 새 빌드 경고는 없었다. SDLPoP 변경은 `53b2ff3`으로 로컬 커밋했다.

상위 구현·테스트·문서는 `207ed1e`로 로컬 커밋했다. 2026-09-20 01:01:48~01:02:01 KST에 현재 장치가 원본 백업 대상과 같음을 다시 확인하고 한 번 업로드했다. 부트로더·파티션·boot_app0·앱의 네 쓰기 해시 검증이 통과했다. 업로드 뒤 장치를 다시 식별하고 5.133초 동안 수신만 해 `USB_FRAME_READY version=1 panel=untouched` 8줄을 확인했다. 01:02:07 KST에 포트를 닫았다. START 패킷은 0회이며 실제 게임 출력은 시작하지 않았다. 사용자에게 첫 한 장의 관찰 준비를 질문한 상태다.

사용자가 사각형 이동 경로의 잔상이 계속 남는다고 보고해 게임 출력은 대기를 유지했다. 현재 상태에서 흰 화면(1bpp 0×8,000바이트) 한 장을 보내면 첫 전체 지우기 한 번 후 추가 그림 없이 전원을 끄고 종료하는 경로임을 확인했다. 이는 기존 `golden` 하네스에서도 검증한 경로이며 펌웨어 변경은 필요 없다. 실제 정리 출력은 아직 실행하지 않았고, 원인 판별을 위한 선행 확인 방법으로만 제안했다. 사용자에게 준비 확인 없이 게임 화면이나 정리 명령을 보내지 않는다.

잔상 완전 소멸 확인 뒤 원래 계획의 게임 한 장 시험을 준비했다. 동일 보드에 `flash_id` 조회와 정상 앱 재부팅만 수행했으며 Flash 쓰기는 없었다. 새 연결에서 READY/panel=untouched 6줄을 확인하고 직렬 포트를 닫았다. 게임 원본 PPM을 제품 호스트로 다시 읽어 기존 bitmap SHA와 같음을 확인했다. 게임 START는 아직 보내지 않았으며 별도 관찰 준비 답변을 기다린다.

## 게임 정지 화면 한 장

송신 원본 8,049바이트에서 START/FRAME 각 1개, CRC와 게임 bitmap SHA 일치를 재확인했다. 시간은 통신·호출 기준이며 물리 패널 전환 완료 시간·실제 fps·입력 지연 측정이 아니다. 첫 전체 정리가 포함돼 이전 사각형의 후속 차분 처리 시간과 직접 비교하지 않는다.

실물 관찰 답변은 **“화면은 보이지만 일부 구분이 어려워요”**였다. 동일한 1bpp 미리보기를 보여 주자 **“미리보기 화면 자체가 좀 이상한가 보네. 미리보기 화면과 보드에 보이는 화면은 동일함”**이라고 확인했다. 원본은 `artifacts/logs/game-single-*`에 보존한다.

### 변환 단계의 세부 손실과 대안

source 46의 RGB PPM과 원본 PNG는 전 픽셀이 같고, 전송 PBM·PNG도 제품의 휘도128 문턱값 결과와 같다. 주요 벽돌의 휘도130은 흰색으로, 어두운 구조물의 휘도29~107은 검정으로 합쳐진다. 빨간 생명력 표시 54픽셀도 휘도55/68이라 모두 검정이 된다. 문턱112는 같은 결과이고 131은 주요 벽돌까지 검정으로 만들어 약98.25%가 검정이므로 문턱 조정만으로 해결하기 어렵다. 이는 전송 이전에 확인한 정보 손실이며 보드의 모든 화질 특성을 검증한 결과는 아니다.

장치 명령 없이 고정4×4 점무늬 후보를 만들었다. 후보 bitmap SHA는 `8cb987bf0acdf4416522c4f96bd1180ac816f86da0fdcca8b4f3011c0e12d424`이며 생명력 영역 54픽셀 중13픽셀이 흰색으로 남는다. 제품 코드와 장치에는 적용하지 않았다. [제안 계획](../.Codex/plans/PLAN-20260920-0237-ordered-monochrome.md)은 승인 전이며, 사용자가 점무늬 외의 방법을 질문해 실제 회색조 대안도 비교했다.

이 보드는 [제조사 사양](https://lilygo.cc/products/t5-4-7-inch-e-paper-v2-3)상16계조를 지원한다. 최초 `first_image` 시험도4bpp 회색조 경로였다. 현재 드라이버의 `epd_draw_grayscale_image()`는 흰 배경을 전제로 한 `epd_draw_image(..., BLACK_ON_WHITE)`이고, 현재 흑백 출력도 같은15단계 호출을 사용한다. 따라서 단순히16계조라는 이유로 현재보다 몇 배 느리다고 단정하지 않는다. 회색→회색의 직접 차분 전환은 현재 USB 코드에 없으며, 한 장 확인과 연속 갱신 구현을 구분해야 한다. 색별 밝기 재배치로 인물·생명력을 강조하는 방법도 가능하지만 두 색만 쓰면 중간 명암 보존에는 한계가 있다.

사용자의 예제 이미지 요청에 따라 같은 source 46을 점무늬 없이16계조로 변환한 Mac 미리보기 `artifacts/usb-game-gray16-preview.png`를 생성했다. 기존 정수 휘도를4비트로 양자화하고 표시용으로0~15를0~255에 대응시켰으며, 보드와 같은2배 정수 확대인640×400이다. 이 장면에는16단계 중14단계가 사용된다. 32,000바이트의4bpp 왕복 변환이 일치함을 확인했다. 실제 패널의 명도·대비를 측정하거나 새 화면을 보드에 전송한 결과는 아니다. 제품 호스트·펌웨어는 변경하지 않았다.

사용자는 이 예시를 확인하고 그대로 보드에 표시하라고 승인했다. 이후 별도 [16계조 정지 화면 시험](16계조-게임-한장-검증.md)으로 같은 픽셀 데이터를 펌웨어에 포함해 한 장을 처리·종료했다. 현재 보드에는 `gray_game`이 설치돼 있다. 이USB v1 소스·앱은 보존했고4bpp USB 프로토콜로 확장한 것은 아니다. 사용자는 생명 화살표가 거의 보이지 않지만 나머지는 훌륭하다고 평가했다. 생명력 표시 대비는 후속 개선 사항이며 연속 전송은 아직 하지 않았다.

## 재현 명령

프로젝트 루트에서 다음 검증을 실행한다. 펌웨어 테스트는 실제 스케치를 포함한 네이티브 모의 환경, 호스트 테스트는 실제 전송 함수와 가상 직렬 포트(PTY)를 사용하며 장치를 구동하지 않는다.

```sh
python3 repos/SDLPoP/tests/test_eink_frame.py
python3 tests/test_usb_frame_firmware.py
python3 tests/test_usb_frame_host.py
```

게임의 실시간 추출은 절대 경로를 사용한다. 같은 파일에는 하나의 게임 프로세스만 기록한다. 정상 게임 종료는 마지막 대기 화면을 저장하지만 강제 종료는 이를 보장하지 않는다. 환경 변수가 없으면 원래 게임 실행 경로로 동작한다.

```sh
EINK_ROOT="$PWD"
mkdir -p artifacts
(cd repos/SDLPoP && SDLPOP_EINK_FRAME_PATH="$EINK_ROOT/artifacts/usb-live.ppm" ./prince megahit 1)
```

다른 터미널에서 아래 미리보기 명령은 보드에 접근하지 않는다. 이미 존재하는 출력 경로는 덮어쓰지 않으므로 새 파일명을 사용한다.

```sh
python3 host/usb_frame.py --frame-path artifacts/usb-live.ppm --preview artifacts/usb-live-preview.pgm
```

빌드·업로드는 [격리 환경 문서](환경-및-검증.md)의 CLI·설정·FQBN을 사용하되 `--library "$EINK_ROOT/repos/LilyGo-EPD47"`, 스케치 `firmware/usb_frame`, 빌드 위치 `.local/build/usb_frame_v2`를 지정한다. 업로드 뒤 READY만 확인해도 패널은 바뀌지 않는다. 직렬 포트는 그때의 CLI 장치 조회·기존 장치 식별 대조로 결정하며 소스에 고정하지 않는다.

아래 전송 명령을 실행하면 START를 보내고 약 20초 선행 검사 뒤 실제 패널이 갱신된다. **화면을 관찰할 준비를 마친 뒤에만 실행한다.** 첫 시험은 1장이고, 12장 시험은 정지 화면 확인 뒤 새 부팅과 별도 준비가 필요하다. 호스트는 자동으로 보드를 재부팅하지 않는다.

```sh
python3 host/usb_frame.py --frame-path artifacts/usb-live.ppm --port "$EINK_PORT" --frames 1
```

`artifacts/logs/usb-frame-*`에 수신 원문·송신 패킷·JSON·첫 PPM/PGM을 보존한다. JSON에는 원본 sequence·파일 mtime·해시, 실제 송신 구간, ACK 응답 시점·보드 시간이 포함된다. Ctrl-C는 진행 중인 프레임의 ACK를 받은 뒤 STOP을 보내며, ACK가 오지 않으면 시간초과로 끝낸다. 오류를 재시도로 해소하려 하지 말고 보드 상태와 원본 로그를 먼저 확인한다.

## USB v2 구현 검증 (2026-09-20)

승인 계획은 [실행 중 16계조 게임](../.Codex/plans/PLAN-20260920-0347-live-gray-game.md)이다. 기존 SDLPoP `53b2ff3`과 드라이버 `f1607da`는 변경하지 않았다. RX 큐는 begin 전에 32,768바이트를 확보해 32,024바이트 단일 FRAME을 받을 수 있게 했다. 최초 약 20초 검사, 12장·30초 새 구동 제한, 오류·종료 후 재시작 금지는 유지했다.

## 첫 실제 게임 연속 시도: 1장 뒤 중단

사용자 “지금 시작” 응답 후 04:03:46 KST에 게임을 재개했다. 선행 검사 20.098889초·199표본이 통과했고 source260의 보정된 4bpp FRAME 한 장을 보냈다. 32,049바이트 TX 원본에는 START 1개와 FRAME 1개만 있으며 길이·CRC·session·seq·payload 해시와 ACK가 일치한다. 두 번째 프레임은 전송하지 않았다.

보드 RX 124.273ms, 표시 처리 1,911.868ms(전체 지우기 1,361.721ms·회색 그림 534.855ms)였다. 호스트가 완전한 ACK를 읽은 시점은 송신 시작 7.039367초 뒤이며 보드 RX+표시보다 5.003226초 늦다. 바로 뒤 약 80µs 간격으로 `rx_timeout` 오류를 읽었고 runtime에는 `DONE reason=error frames=1 applied=1`이 남았다. 정상 완료 후 10초 관찰은 수행되지 않았다. 다운로드 모드 중단 명령은 코드 0, 해당 게임은 04:04:25에 강제 종료 없이 코드 0으로 종료하고 PPM 임시 파일도 정리했다. 이 결과는 12장 연속 성공이나 실제 입력 반응 확인이 아니다.

ACK는 CRLF 포함 151바이트로 64배수 메시지가 아니다. 코어2.0.17 HWCDC의 연결 미확인 경로에는 송신 IRQ 활성화가 큐 기록보다 먼저 일어나는 경로가 있어, 뒤의 오류 출력이 정체된 응답을 밀어냈을 가능성이 있다. 해당 연결 상태를 직접 기록하지 않아 원인을 확정하지 않는다. 단순 `flush()`는 연결 실패 때 큐를 버리므로 송신 보장으로 해석할 수 없다.

같은 연동 범위에서 ACK 전 연결 확인을 최대100ms 수행하고 ACK 뒤 flush·연결 재확인 뒤 RX 대기를 시작하도록 보완한다. 화면 처리·CRC·프레임 수·5초 RX 제한은 변경하지 않는다. 사용자에게 Mac 창 전환 시간이 필요하다는 피드백을 받아 다음 시도에는60초 준비 구간을 별도로 둔다. 이번 RX 시간초과는 키 입력과 무관하다. 재시험 결과는 별도로 기록한다.

응답 보완 후 실제 스케치 native 검증43개가 ASan/UBSan으로 통과했다. ACK를 flush 전까지 모의 큐에 남겨 송신 순서를 검사하고, 4ms 후 연결 회복·100ms 연결 실패·flush 중 연결 손실과 큐 유실을 포함한다. 수정판 앱281,536바이트 SHA는 `7821bb0ddf45044605776e9e7af35499c44a6521ca9fda439e739ac515796a45`, 스케치 SHA는 `4dd2a01705ff1a17c14430526a4bf75d5b4455611d1ed1d3f5b918f83d179ea4`다. 빌드 스케치와 검증 소스가 일치하고 드라이버22개 단위를 확인했다. 이는 코드·메모리 검증이며 실제USB 문제가 해결됐다는 판정은 재시험 이후에만 한다.
