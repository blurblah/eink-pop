# 드라이버 병목 분석과 최소 수정 후보

2026-09-27. 승인된 소스 분석·호스트 검증·빌드 단계 완료. 장치 업로드·패널 동작은 하지 않았다.

## 결론과 선택한 후보

현재 방식은 작은 변화에도 흰색15단계·검정15단계, 총30회 패널 주사를 실행한다. 넓은400행 갱신은 현재10MHz·행당248바이트 전송만 약299ms다. 따라서 **현재 단계 수·행 전송 방식을 그대로 두고 CPU 대기만 줄여서는 넓은 장면을10fps로 표시할 수 없다.** 패널 자체의 절대 한계나 새 파형의 한계라고 일반화하지 않는다.

이번에는 전송 완료 콜백의 잘못된 ISR yield 요청만 고쳤다. 화면 정보·파형·단계 수·전원 순서·DMA 완료 보호는 그대로다. 원인과 수정 범위가 명확하고 독립 비교가 가능한 첫 후보이며,687ms 병목 전체의 원인이나10fps 해결책으로 판정한 것은 아니다.

## 실행 경로와 비용의 구분

현재 보드는 S3, 프로젝트 코어2.0.17·SDK 표기4.4.7-dirty·CPU240MHz이다. 해당 S3 qio_opi SDK 헤더의 `CONFIG_FREERTOS_HZ=1000`을 확인했다. `USER_I2S_REG=0`이므로 이름과 달리 예전 I2S 레지스터 직접 구동 경로가 아니라 LCD I80 SDK 경로를 사용한다.

- `epd_draw_image`: 호출당10tick 요청 후15단계. 단계마다 생산자/소비자 태스크 생성, 두 완료 세마포어 대기, 두 태스크 삭제,5tick 요청.
- `provide_out`: 매 단계 LUT 갱신, 해당 영역의 행을 큐로 전달하고5tick 요청 뒤 완료 통지.
- `feed_display`: 매 단계 패널540행을 순회한다. 영역 내부는480바이트 입력 행을 받아240바이트 전극 명령으로 변환하고, 영역 외부도 CKV를 진행한다. 매 단계 시작/종료 펄스도 있다.
- `epd_output_row`: 앞선 DMA 완료를 기다리고 latch·CKV 요청 뒤248바이트를 LCD 버스로 보낸다. 현재 단일 버퍼의 완료 전 덮어쓰기 방지는 유지한다.
- `epd_skip`: 빠른 스킵도 한 행마다 RMT 호출한다. 스킵 진입 첫 두 행은 파이프라인 정리용 일반 출력이고, 이후부터 짧은 CKV 펄스다.

SDK4.4.7의 `rmt_write_items(..., false)`도 시작 전에 이전 전송의 세마포어를 기다린다. `false`는 이번 전송의 완료까지 기다리지 않는다는 뜻이지, 모든 호출 비용이나 이전 전송 대기가 없다는 뜻이 아니다. 같은 RMT 채널의 펄스는 직렬이다. [ESP-IDF4.4.7 RMT 소스](https://raw.githubusercontent.com/espressif/esp-idf/v4.4.7/components/driver/rmt.c)

## 재현 가능한 호출 예산

```sh
python3 host/driver_budget.py --y 70 --rows 64
python3 host/driver_budget.py --y 70 --rows 400
python3 tests/test_driver_budget.py
```

소스4개의 SHA-256이 검토한 버전과 다르면 계산을 거부한다. 표는 앞선 단계가 아래쪽 스킵 구간에서 끝난 정상 반복 상태다. 첫 전체 지우기 직후 상태는 별도 결과로 출력하며64행 기준 DMA2회가 추가된다. `time_prediction_us`는 의도적으로null이다.

| 항목 | 64행 | 400행 | 해석 |
| --- | ---: | ---: | --- |
| 극성별 단계 합계 | 30 | 30 | 흰색15+검정15 |
| 태스크 생성/삭제 | 각각60 | 각각60 | 생성 비용은 미측정 |
| 입력 큐 송신/수신 | 각각1,920 | 각각12,000 | 한 항목480바이트 |
| 전체 RMT 요청 | 16,380 | 16,380 | 활성·스킵·프레임 제어 포함 |
| LCD 행 전송 | 1,980 | 12,060 | 영역 행 외 파이프라인 정리 포함 |
| LCD 데이터 전송량 | 491,040바이트 | 2,990,880바이트 | 248바이트/전송 |
| LCD 순수 데이터 직렬 시간 | 49.104ms | 299.088ms | 8비트 버스10MHz, 명령·빈 주기·CPU 비용 제외 |
| 프로그램된 RMT 펄스 길이 합 | 92.375ms | 145.127ms | 10MHz RMT, CPU·호출 간격 제외 |
| 호출자 대기 요청량 | 170ms | 170ms | 2×10 + 30×5tick |
| 생산자 대기 요청량 | 150ms | 150ms | 30×5tick, 소비자와 겹침 |

**LCD 시간과 RMT 시간을 합산하지 않는다.** 서로 겹칠 수 있다. 생산자150ms도 소비자와 겹치며, tick 요청량은 실제 정지 시간과 같지 않다. 작업 생성·LUT·큐·변환·인터럽트·스케줄링을 기존687.038ms에서 정확하게 분리할 계측은 없다.

예컨대687ms에서170ms를 산술적으로 빼면517ms, 중복을 무시하고320ms를 빼도367ms다. 이는 속도 예측이나 보장 하한이 아닌 비용 규모 비교다. 이런 계산을 “수정하면367ms가 된다”로 해석하지 않는다.400행의299ms 전송량은 기존 좁은30~102행 경험식의 외삽이 아니라 현재 코드와 버스 설정의 계산이다. 실제400행 측정은 하지 않았다.

## 완료 콜백 수정의 근거

기존 `notify_trans_done()`은 `output_done=true; return output_done;`였다. 이 함수는 FreeRTOS 태스크를 깨우는 API를 호출하지 않고 완료 플래그만 설정한다. SDK 헤더에서 콜백 반환값은 이 함수가 높은 우선순위 태스크를 깨웠는지를 뜻한다. 수정은 플래그를 그대로 설정한 뒤 `false`를 반환한다. [ESP-IDF 콜백 계약](https://raw.githubusercontent.com/espressif/esp-idf/v4.4.7/components/esp_lcd/include/esp_lcd_panel_io.h)

SDK ISR은 이 반환값이true면 yield를 요청한다. SDK 내부 큐 송수신이 실제로 태스크를 깨웠을 때의 yield 판정은 별도로 유지되므로, 콜백의false가 필요한 모든 스케줄 전환을 막는 것은 아니다. [ESP-IDF I80 ISR](https://raw.githubusercontent.com/espressif/esp-idf/v4.4.7/components/esp_lcd/src/esp_lcd_panel_io_i80.c)

64행 양극성 예시에서 불필요하게 추가하던 요청은1,980회다. 이것은1,980회의 실제 컨텍스트 전환이나 그에 해당하는 시간 절약을 보장하지 않는다. 현재 작업이 계속 선택될 수도 있으므로 실제 이득은 측정해야 한다.

- 하위 브랜치: `codex/eink-pop-lcd-callback`
- 하위 커밋: `9b8dcdba04ed03ee70dba412667803b1dac1adfd`
- 변경: `src/i2s_data_bus.c` 콜백 반환 한 줄과 설명 주석. 기존CRLF 보존.
- USB 스케치 변경: 드라이버 식별자 두 곳만 새 커밋으로 변경.
- 기존 오프라인 보정 프로필은f1607da의 실측이므로 그대로 보존한다. 새 드라이버 결과를 이전 실측으로 인증하지 않는다.

다음 단계에서 두 코어 동기화·RMT/DMA 구조·새 파형을 구현한다면 High를 권장한다. 이번 계약 수정과 계산 검증은 Medium으로 진행했다. Ultra가 필요한 근거는 현재 없다.

## 검증과 산출물

- `tests/test_lcd_callback.py`: 실제 C 콜백을 추출해 컴파일. 수정 전 `!yield` assertion 실패(-6) 재현, 수정 후 완료 플래그·반복 호출·false 반환 통과.
- `tests/test_driver_budget.py`:6개 테스트 통과. 영역 안/밖·최상단/최하단·풀스크린 마지막 행·스킵 상태·소스 변경 거부 확인.
- `tests/test_bw_interleaved_driver.py`: 기존 C 드라이버22개 파이프라인 사례·LUT·DMA 보호·잘못된 입력·생성 실패 검증 통과. 실제 RTOS 동시성 검증은 아니다.
- `tests/test_usb_frame_firmware.py`: 실제 수신 스케치47개 시나리오·ASan/UBSan 통과.
- 기존 설정의 ESP32-S3 빌드 성공. 기존 드라이버 `round()` 선언 관련 경고는 남아 있으며 이번 범위에서 변경하지 않았다.
- `.local/build/usb_frame_v3_callback/usb_frame.ino.bin`:281,840바이트, SHA-256 `14e2283dd41b8fcfcb3e35021bc3fd3409e98525f37baf3a553b88f370960c48`.
- 빌드 의존성에서 실제 하위 저장소의 `i2s_data_bus.c` 사용을 확인했고 앱에 새 드라이버 식별자가 포함된 것을 확인했다.
- 계산 JSON·빌드 로그·산출물 해시: `artifacts/driver-budget-20260927/`.

장치에는 기존f1607da 기반 앱이 남아 있다. 컴파일 성공과 호스트 테스트는 속도 개선·실물 화면 검증을 대체하지 않는다.

## 다음 단일 비교 시험의 조건

1. 사용자 관찰 준비 후 기존 v3 시험의 동일12개1bpp payload·순서·250ms 대기를 재현한다. 새 게임 입력을 섞어 시간 차이를 비교하지 않는다.
2. 업로드 전 현재 포트·보드·백업·앱 해시를 확인한다. 새 드라이버 설정 로그를 기록하고 시작 전에는 패널을 구동하지 않는다.
3. 처음 한 번 전체 지우기, 최대12장, 기존 장치 시간 제한·종료 후10초 무갱신 확인을 유지한다. 반복 속도 시험은 하지 않는다.
4. 같은 행 높이의 white/black/display 시간을 이전 로그와 대응시키고 화면 누락·흐림·잔상·깜빡임을 확인한다. 광학 응답 속도와 호출 시간을 구분한다.
5. 큰 개선이 없으면 이 후보를10fps 해결책으로 계속 반복 시험하지 않는다. 새 파형 또는 버스 구조 개발의 비용을 판단한다. 오류·미종료면 해당 시험만 중단하고 기존 앱으로 복구한다.

이 시험은 준비 조건이며 아직 수행하지 않았다. 현재 확보한 데이터만으로 새 파형의 속도나 이득을 수치로 약속하지 않는다.
