# 흰색·검정 단계 교차 갱신 검증

작성일: 2026-09-20, Asia/Seoul. [계획](../.Codex/plans/PLAN-20260920-0010-interleaved-bw-update.md)은 최적화 설명 뒤 사용자의 “진행해” 지시를 실행 승인으로 기록한다.

## 목적과 현재 상태

이전 차분 시험은 큰 영역의 깜빡임을 줄였고 마지막 정사각형도 정상으로 남았다. 흰색으로 먼저 지운 뒤 검정색을 그리는 두 호출 사이에 폭 16픽셀만 남는 것은 알고 선택한 중간 상태였다. 이번 작업은 그 방식의 추가 최적화이며, 이전 시험이 의도와 다르게 동작했다는 의미가 아니다.

소스 구현·ESP32-S3 빌드·호스트 검증과 같은 장치의 1회 업로드를 마쳤다. 사용자 관찰 준비 답변 뒤 RUN을 한 번 보내 12프레임 시험을 실행했고 12.401029초에 종료됐다. 종료 후 10.050초 동안 추가 실행 로그가 없었다. 사용자는 중간 좁아짐 감소와 일부가 구분돼 보이는 현상, 조금 더 심한 잔상, 큰 영역 깜빡임 없음과 멈춤을 확인했다. 처리 속도 향상도 없어 교차 방식을 다음 단계의 기본값으로 채택하지 않는다.

## 선택한 방식

제조사 검정·흰색 모드의 15단계 시간 배열은 서로 다르다. 한 시간표로 둘을 동시에 구동하면 한쪽 구동 조건이 달라진다. 이번에는 각 색의 시간값을 유지하면서 처리 순서만 짧은 단계마다 교차한다.

| 항목 | 이전 차분 출력 | 이번 교차 출력 |
| --- | --- | --- |
| 후속 프레임의 호출 | 흰 복원 호출 → 검정 추가 호출 | 교차 API 한 번 |
| 주사 순서 | 흰색 15단계 완료 → 검정 15단계 완료 | 흰색 0 → 검정 0 → 흰색 1 → 검정 1 → … |
| 후속 프레임 주사 수 | 30 | 30 |
| 색별 시간값·횟수 | 제조사 기본값 | 같은 기본값 |
| 각 주사 후 대기 | 5tick | 5tick |
| 같은 색의 다음 단계까지 간격 | 같은 색이 연속됨 | 다른 색의 주사·대기가 사이에 들어감 |
| API 진입·세마포어 준비 | 두 번 | 한 번 |

완전히 동시 출력하거나 주사 횟수를 절반으로 줄이는 방식은 아니다. 중간 좁아짐이 얼마나 줄어드는지, 휴지 간격 변화가 잔상에 어떤 영향을 주는지, 호출 시간이 얼마나 달라지는지는 실물 시험으로 판단한다. 색별 시간값을 보존해도 전체 물리 파형이 동일하다고 볼 수 없다.

## 입력과 시험 조건

새 `epd_draw_bw_interleaved()`는 전체 폭의 정렬된 4bpp 버퍼만 받는다. 한 픽셀의 nibble이 0이면 검정, 1이면 흰색, 2~F이면 무동작이다. x=0·width=960, 유효한 y·height, null이 아닌 4바이트 정렬 포인터를 검증한다. 일반 회색조 API가 아니며 기존 세 모드는 유지한다.

| 항목 | 설정 |
| --- | --- |
| 실물 | Screen-4.7-S3 V2.4 2024-12-03, ESP32-S3 |
| 패널·마스크 영역 | 960×540 / x=0, y=238, 960×64 |
| 마스크 버퍼 | PSRAM 30,720바이트, 행당 480바이트 |
| 사각형 | 64×64, 전역 x=184+48×인덱스, y=238 |
| 첫 프레임 | F 배경·0 사각형, 기존 검정 모드 1회 |
| 이후 프레임 | F 배경·떠나는 48×64에 1·들어오는 48×64에 0, 교차 API 1회 |
| 시작·제한 | 부팅당 RUN 1회, 화면 전 20초 지연 검사, 최대 12프레임 |
| 정지 조건 | 최초 화면 전원 켜기부터 30초가 지나면 새 프레임 시작 금지 |
| 초기화·대기 | 최초 전체 지우기 1회, 매 프레임 전원 끄기·250ms 대기 |

첫 프레임은 15주사, 후속 11프레임은 각 30주사다. 초기 전체 지우기 주사는 별도다. 실패하면 추가 프레임을 출력하지 않으며, 종료 후 RUN을 다시 보내도 재실행하지 않는다.

## 함께 확인한 출력 경로의 문제

`skip_row(uint8_t)`가 받은 300은 44로 줄어든다. 이전 64행 영역에서도 마지막 유효 행을 내보내는 경로가 해당한다. 인수를 넓혀 시간값을 유지하면 이 행의 마지막 단계 조건이 이전 실물 시험과 달라진다. 교차 순서만 바꾼 비교라고 표현하지 않는다.

S3 드라이버는 단일 전송 버퍼를 사용하지만, 다음 행을 쓰는 시점이 이전 전송의 완료 확인보다 앞설 수 있다. [ESP-IDF 4.4.7 문서](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/peripherals/lcd.html#_CPPv425esp_lcd_panel_io_tx_color25esp_lcd_panel_io_handle_tiPKv6size_t)는 DMA 전송 완료 후 버퍼를 재사용하도록 정한다. 버퍼를 반환하기 전과 프레임 종료 전에 전송 완료를 기다리도록 수정한다. 실제 장치의 픽셀 오염을 관찰했다는 주장은 아니다.

새 작업의 독립 리뷰에서 소비자 작업 생성 실패 시 다른 코어의 생산자가 정리 도중 매개변수에 접근할 가능성을 확인했다. 새 API 전용 두 작업은 시작 통지를 기다리는 wrapper로 진입하고, 두 작업이 모두 생성된 뒤에만 통지를 받는다. 통지 전에는 스택 매개변수·큐·완료 세마포어에 접근하지 않는다. 기존 `epd_draw_image()` 본문은 변경하지 않았다.

드라이버 호스트 검증은 실제 작업 소스의 API·생산자·소비자·변환·행 건너뛰기·프레임 종료·S3 버퍼 반환 함수를 추출해 실행했다. 65,536개 LUT 조합의 네 픽셀, 30주사의 극성·단계·시간표, 전체 행의 모든 픽셀, 행 복사·순서, 큐 소진, 마지막 행 flush와 입력 버퍼 가드를 확인했다. 기준 `86be1ba`의 300→44 축소·DMA 중 버퍼 조기 반환·조기 종료 제어를 모의 전송으로 재현했고 수정본은 통과했다. 실제 RTOS 동시성이나 장치의 과거 오출력을 재현한 것은 아니다.

새 시험 관찰기는 장치 없는 모의 입력으로 누적 준비 로그·정상 12프레임·종료 후 10초, 실행 후 재부팅 표식과 실패 종료를 확인했다. RUN 한 번·직렬 닫기·원본 바이트 보존을 검증했다. 실제 사용 때는 업로드와 관찰 시작을 분리하며, 오류 중단과 메타데이터 저장은 실행 측에서 수행한다.

최종 앱 `.local/build/bw_interleaved/bw_interleaved.ino.bin`은 282,304바이트, SHA-256 `4288737380d4f1d33c38d127156fb19a44d372533c87d460ff816656497c0511`이다. 기존 제조사 `round` 선언 경고 외 새 경고는 없었다. 원본 컴파일 로그, 소스별 SHA-256, 산출물 목록과 ELF 발췌는 `artifacts/logs/bw-interleaved-*`에 보관한다. 시작 통지 보강 전 빌드 로그는 `bw-interleaved-compile-initial.log`로 따로 보존했다.

출고 백업은 `artifacts/firmware-backups/factory-20260919.bin`, 16,777,216바이트, SHA-256 `f0944ec95db31e8aa21a9cab0fdb08cc8a962b2f66f3d3733a88a3b8f95762f8`이다. 직전 차분 앱 `.local/build/bw_delta/bw_delta.ino.bin`은 281,232바이트, SHA-256 `8d1f0a8bfd72774a4ca3fdb54d85f09588761ef4a80cf3dc4a002ccb8b1d2464`이다. 이번 작업 시작 때 실제 파일의 크기·해시를 대조했다.

드라이버 작업 브랜치는 `codex/eink-pop-interleaved-update`이며 `86be1ba`에서 시작해 구현을 `f1607da`에 커밋했다. 원본 제조사 저장소와 별도 SDLPoP 원본의 HEAD·브랜치·상태·diff·파일 해시가 이관 전 기록과 같은지 확인했다. 관련 변경은 로컬 커밋하며 push하지 않는다.

스케치·테스트·빌드 근거와 드라이버 참조는 상위 `37c651c`에 커밋했다. 업로드 직전 같은 USB 장치를 재조회하고 출고 백업·첫 이미지·직전 차분 앱·새 빌드 해시를 확인했다. 쓰기 네 구간 검증 뒤 별도 직렬 연결에서 `INTERLEAVED_READY ... panel=untouched`를 받고 포트를 닫았다. 준비 확인 과정에서 RUN을 보내지 않았다. 근거는 `bw-interleaved-upload.log`, `bw-interleaved-upload-metadata.json`, `bw-interleaved-ready-before-run.log`, `bw-interleaved-build-identity.json`이다.

프로젝트 루트에서 호스트 검증을 실행한다.

```sh
python3 tests/test_busy_delay.py
python3 tests/test_bw_delta.py
python3 tests/test_bw_interleaved.py
python3 tests/test_bw_interleaved_driver.py
```

빌드는 [이전 차분 시험](지연-수정과-차분-갱신-검증.md#실행과-재현)의 CLI·설정·FQBN을 그대로 사용하고, 스케치를 `firmware/bw_interleaved`, 빌드 경로를 `.local/build/bw_interleaved`로 지정한다. `--library "$PWD/repos/LilyGo-EPD47"`를 명시한다. 포트는 매번 조회하며 업로드와 RUN 전송을 분리해 관찰 준비 전 화면 출력이 시작되지 않게 한다.

## 실제 장치 시험

사용자가 “준비됐어요, 지금 시작”이라고 답한 뒤 장치를 다시 조회했다. 2026-09-20 00:30:15 KST에 RUN을 한 번 보냈다. 시작 전 누적 준비 로그 3줄은 재실행을 유발하지 않았고, START·지연 검사 종료·DONE은 각 1개였다. 패널 구동 전 20.098789초 검사에서 199개 표본을 수집했고 부호 0/1 표본은 88/111개였다.

프레임 0은 기존 검정 호출 한 번, 1~11은 교차 API 한 번으로 출력됐다. `frame_limit`으로 12.401029초에 끝났으며 마지막 좌표는 x=712, y=238이다. RUN 이후 직렬 관찰은 42.561초, 종료 뒤 관찰은 10.050초였고 00:30:58에 포트를 닫았다. 오류 중단·재시도·복구는 하지 않았다.

후속 프레임 처리 평균은 714.124ms, 첫 구간 제외 시작 간격 평균은 964.000ms였다. 직전 차분 재시험의 682.123ms·932.000ms보다 각각 약 32ms 길었다. 이번 빌드에서는 처리 속도 향상을 확인하지 못했다. 교차 순서 외에도 마지막 행 시간값·DMA 완료 대기 보정이 포함된 비교이므로 증가분 전체를 교차 방식 하나의 비용으로 단정하지 않는다. 실물의 중간 모양·잔상 효과는 사용자 관찰을 따로 기록한다.

사용자 보고는 다음과 같다. 같은 답변이 두 번 전달됐으므로 한 차례 관찰로 기록한다.

- 가늘어지는 모습은 줄었지만 사각형 일부가 따로 구분된 느낌으로 여전히 티가 남.
- 잔상은 이전보다 조금 심해짐.
- 큰 영역 깜빡임은 없음.
- 사각형은 멈춰 있는 상태.

따라서 중간 모양의 일부 개선은 있었으나 잔상과 처리 시간까지 종합한 개선은 확인하지 못했다. 최종 폭의 별도 수치 측정이나 정사각형 여부의 추가 질문은 하지 않았다. 교차 API와 소스 변경은 실험 이력으로 보존하고, 기존 API도 유지한다. 사용자 답변 뒤 추가 시험·임의 파형 조정·펌웨어 복귀는 하지 않았다.

USB 펌웨어 업로드 후 첫 게임 화면 시작을 기다리는 동안 사용자가 “사각형 잔상이 이동한 경로에 따라 남아 있다”고 추가 관찰했다. 직전 사각형 시험은 최종 화면을 유지하려고 종료 후 전체 지우기를 하지 않았고, USB 업로드 후에도 START를 보내지 않아 패널은 갱신되지 않았다. 따라서 부분 갱신의 잔상과 부합하지만, 전체 정리 후의 실제 화면을 확인하지 않아 제품 불량·영구 손상 여부는 판정하지 않는다. 이동 중 의도된 중간 모양과 종료 후 남는 잔상은 별개다.

제조사 [제품 안내](https://lilygo.cc/products/t5-4-7-inch-e-paper-v2-3)는 장시간 부분 갱신의 잔상·복구 불가 손상을 경고하며, [공식 위키](https://wiki.lilygo.cc/products/t5-series/t5-e-paper/)에도 전체 갱신을 통한 잔상 제거 예제가 소개돼 있다. 이번 추가 관찰 뒤 장치 명령은 보내지 않았다. 다음 판정 방법으로 제조사 전체 지우기 한 번 후 흰 화면에서 흔적을 확인하는 것을 제안한다. 반복 구동이나 잔상 제거 성공을 미리 전제하지 않는다.

원본 근거는 `artifacts/logs/bw-interleaved-runtime.log`, `bw-interleaved-observation.json`이며 재계산 결과는 `bw-interleaved-measurements.json`이다. 로그 순서·좌표·모드·구간 합·통계·제한·지연·업로드 해시를 대조한 35개 항목이 통과했다. 지연 표본의 최소값은 120,020cycle로 요청 120,000cycle 이상이었다. 업로드는 00:27:25~00:27:39 KST에 수행했다. 드라이버 호출 간격을 실제 패널 fps로 표현하지 않는다.

## 한계와 다음 판단

호스트의 결정적인 큐·태스크 모의 실행은 실제 RTOS 동시성이나 전압 파형을 검증하지 않는다. 전체 파형 최적화, 대기 시간 단축, 1bpp, USB 화면 전송과 게임 연동은 이번 변경에 섞지 않는다.

교차 방식은 다음 단계의 기본 갱신 방식으로 채택하지 않는다. 이 결과는 동일한 저수준 보정을 적용한 두 방식끼리의 비교가 아니므로, 잔상 변화의 원인을 교차 순서 하나로 확정하지 않는다. 새로운 비교나 USB 화면 전송 구현은 별도 후속 계획에서 정한다. 제조사의 장시간 부분 갱신 주의사항은 계속 적용되며, 이번 횟수 제한이 패널의 무손상을 보장하지 않는다.
