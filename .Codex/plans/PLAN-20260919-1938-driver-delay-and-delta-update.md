## 요청 사항

> 제한 흑백 애니메이션 다음 단계로 진행한다. 발견한 시간 지연 결함을 수정하고 큰 영역의 반복적인 검정·흰색 반전을 줄일 수 있는지 검증한다.

이전 계획은 완료됐으며 제조사 드라이버 수정과 다른 출력 방식은 당시 승인 범위에서 제외됐다. 이번 계획은 최소 수정, 소프트웨어 검증, 같은 장치의 한 차례 제한 시험을 묶는다. 사용자가 이 계획에 이어 두 저장소를 프로젝트 하위로 가져와 작업 브랜치에서 진행하고, SDLPoP 기존 변경을 이관하며 모든 변경을 커밋하되 push하지 말라고 지시했다. 이 지시를 실행 승인 및 저장소 관리 방식 수정으로 반영한다.

## 가정 및 제약

- 대상은 기존 `Screen-4.7-S3 V2.4 2024-12-03` 한 대다. 포트·장치 식별자는 업로드 직전에 다시 확인한다.
- Arduino CLI 1.5.1, 프로젝트 ESP32 코어 2.0.17, 240MHz·OPI PSRAM·16MB Flash 설정을 유지한다. 전역 ESP32 3.3.7과 별도 SDLPoP, `.serena/` 등 무관한 파일을 보존한다.
- 제조사 기준 커밋은 `50224221fb81a8fcf9068532374b775af84a38d4`다. 현재 `.local/libraries/LilyGo-EPD47` 원본에는 변경이 없다.
- 4bpp의 기존 `BLACK_ON_WHITE`·`WHITE_ON_BLACK`와 각 15단계 기본 파형을 사용한다. 파형 값·주사 횟수·주파수·전원 순서를 임의로 변경하지 않는다.
- 1bpp는 `mode` 무시와 행 종료·S3 데이터 순서 검토가 필요하므로 제외한다. USB 픽셀 전송, 게임 연동, 추가 하드웨어도 제외한다.
- 제조사는 장시간 부분 갱신의 잔상·복구 불가 손상을 경고한다. 이번 횟수 제한은 시험량을 줄이는 조치이며 안전이 검증된 임계값은 아니다.
- 제공 스킬 중 이 ESP32 드라이버 작업에 직접 적용할 스킬은 없다. 재현 절차는 프로젝트 문서·패치·테스트로 보존한다.

## 최소 지연 수정과 검증

- `repos/LilyGo-EPD47`의 고정 커밋에서 작업 브랜치를 만든다. 바뀌는 제조사 파일은 `src/ed047tc1.c` 하나, 함수는 `busy_delay()` 하나다. 별도 패치 파일 대신 Git 커밋을 정본으로 삼는다.
- `uint64_t` 목표값과 signed 카운터를 비교하는 대신 시작값을 `uint32_t`로 읽고 `uint32_t` 경과량을 요청 cycle 수와 비교한다. `IRAM_ATTR`·호출처·시그니처는 유지한다.
- `epd_driver.c:887`의 비슷한 대기는 주석이므로 수정하지 않는다.
- 호스트에서 실제 함수 본문을 추출해 C로 컴파일한다. 모의 CCOUNT 반환형은 SDK처럼 signed 32비트로 유지한다. 지연 0·1·240·2,400·24,000·120,000cycle 및 0·부호 경계 전후·음수 구간·32비트 순환 전후를 조합한다. 요청 직전에는 대기하고 도달·초과 시 반환하는지 검증하며 모의 읽기 횟수를 제한한다.
- 원본의 실패 사례와 수정본의 통과 사례를 함께 기록한다. 테스트를 위해 실제 CPU 카운터를 덮어쓰지 않는다.
- 빌드 시 `repos/LilyGo-EPD47`을 명시하고 컴파일 데이터베이스·의존성 파일에서 선택 경로를 확인한다. 최종 ELF의 `busy_delay`가 unsigned 경과량 비교인지 확인한다.

## 화면 구동 전 장치 검사와 시작 조건

- 부팅·재부팅만으로 패널을 초기화하거나 그림을 출력하지 않는다. 직렬 연결 후 준비 로그를 반복하고 정확한 `RUN` 한 줄을 받아 부팅당 한 번만 실행한다. 시작 문자는 시험 제어용이며 USB 픽셀 전송 구현이 아니다.
- Mac은 준비 로그를 확보하고 사용자에게 관찰 시작을 안내한 다음 시작 문자를 한 번 보낸다. 이로써 이전 시험에서 놓친 시작 로그를 확보하고 자동 재부팅에 따른 시험 반복을 막는다.
- 시작 후 패널 초기화 전에 실제 `busy_delay(120000)`를 약 100ms 간격으로 20초간 호출한다. 현재 240MHz에서 500µs 요청이다. CPU 코어·주파수, 카운터 최상위 비트가 0/1인 표본, unsigned 경과 cycle과 `esp_timer` 경과를 기록한다.
- 양쪽 부호 구간의 표본이 있고 모든 요청이 최소 cycle 수를 지켰을 때만 화면 단계로 넘어간다. 호출이 느린 경우를 무조건 실패로 간주하지 않고 인터럽트 등의 영향과 함께 기록한다. 이 검사는 전압 순서의 계측이 아니다.
- 버퍼 할당·주파수·지연 검사가 실패하면 패널 초기화 없이 종료한다. 지연 검사 단계가 25초를 넘으면 추가 호출을 시작하지 않고 종료한다. 내부 함수가 반환하지 않는 경우는 호스트의 중단 절차를 따른다.

## 갱신 방식과 제한 시험

| 항목 | 설정 |
| --- | --- |
| 보드·패널 | 기존 ESP32-S3, 960×540 |
| 기존과 같은 이동 범위 | 중앙 640×400 안, 사각형 64×64, 전역 y=238, 전역 x=184+48×인덱스 |
| 마스크 전달 영역 | `Rect_t{0, 238, 960, 64}` |
| 버퍼 | PSRAM 30,720바이트, 행당 480바이트, 4bpp; 두 패스에 재사용 |
| 초기 상태 | 패널 초기화 1회, 전체 지우기 1회 |
| 첫 프레임 | 전체 버퍼 F, 첫 64×64만 0으로 채워 `BLACK_ON_WHITE` 출력 |
| 후속 흰 복원 | 전체 버퍼 0, 이전 사각형의 왼쪽 48×64만 F로 채워 `WHITE_ON_BLACK` 출력 |
| 후속 검정 추가 | 전체 버퍼 F, 새 사각형의 오른쪽 48×64만 0으로 채워 `BLACK_ON_WHITE` 출력 |
| 겹치는 부분 | 16×64는 두 패스 모두 무동작 |
| 프레임 전원 | 켜기 → 필요한 패스 1~2회 → 끄기 → 250ms 대기 |
| 횟수 | 부팅당 1회 시험, 최대 12프레임; 그리기 호출 최대 23회 |
| 화면 시간 제한 | 최초 패널 전원 켜기부터 30초에 도달하면 다음 프레임 시작 금지 |
| 종료 | 마지막 그림 유지, 전원 끄기 함수 반환, 추가 갱신 없음 |

**행 전체를 보내되 바뀌는 픽셀만 구동하도록 마스킹한다.** 작은 Rect에 `WHITE_ON_BLACK`을 바로 쓰면 제조사 코드가 좌우 여백을 F로 채워 같은 행의 주변도 흰색 구동 대상이 된다. 전체 폭 분기를 사용하면 이 패딩 경로를 피한다. LUT에서 `BLACK_ON_WHITE`의 F와 `WHITE_ON_BLACK`의 0은 모든 출력 단계에서 무동작이다.

각 패스마다 버퍼 전체를 초기화하고 이전 마스크를 남기지 않는다. 첫·마지막 위치, 바뀌는 48×64 띠, 겹침 16×64, 주변 픽셀, 4바이트 정렬·stride를 실제 코드로 검증한다. 두 패스 사이에는 잠깐 폭 16픽셀만 남는 중간 상태가 가능하다. 흰색 복원 정도·잔상·실물 속도·깜빡임 감소는 아직 검증하지 않았다.

## 위험 및 롤백

- 제한된 부분 구동에도 잔상·깜빡임 위험이 있다. 파형의 물리적 적합성을 호스트 테스트나 호출 시간만으로 보장하지 않는다.
- 30초·25초 조건은 새 작업 시작을 막는 소프트웨어 조건이며, 실행 중인 드라이버의 무한 대기를 강제 종료하지 않는다. 오류·재시작·관찰 한도 초과 시 다운로드 모드로 중단하고 로그를 보존한다. USB 제어가 안 되면 사용자에게 전원 분리를 요청한다.
- 실패·잔상에 대응해 펄스 세기·횟수를 임의로 조절하거나 반복 지우기·시험을 추가하지 않는다.
- 소스 롤백은 새 작업 브랜치의 변경 커밋과 상위 참조에 한정한다. 제조사 기준 브랜치, 원래 SDLPoP 작업 트리와 기존 바이너리는 계속 보존한다. 사용자 변경을 자동으로 되돌리거나 기존 브랜치를 강제로 이동하지 않는다.
- 펌웨어 복귀가 필요하면 보존한 첫 정적 이미지 또는 출고 백업 복구 절차와 그 영향을 먼저 확인한다. 첫 시험 바이너리에도 원본 지연 함수가 들어 있으므로 이를 결함 수정 상태로 부르지 않는다. 펌웨어 복원이 패널 잔상의 복구를 보장하지 않는다.

## 실행 기록

사용자의 저장소·브랜치·커밋 지시를 반영해 실행을 시작한다. SDLPoP 기준은 `3c5add5fb7f83d4ceb542823ab66d00146c4271b`, 기존 작업 변경은 `src/common.h`의 `<strings.h>` 추가 1줄이며 staged·untracked 변경은 없다. 드라이버 원본은 shallow clone인 점을 보존 기록에 명시한다.

저장소 준비 결과:

- 상위 초기 검증 기록을 `374ec38`로 커밋하고 `codex/eink-pop-development`를 생성했다.
- 두 저장소를 `repos/` 아래 독립 복제하고 공식 origin URL과 submodule 등록을 확인했다. Git 객체의 hardlink·alternates 의존이 없다.
- SDLPoP 기존 변경을 `codex/eink-pop-integration`의 `bbf16fc`로 커밋했다. 원본과 새 파일 바이트가 같고, 원본 HEAD·브랜치·상태·diff·파일 해시는 변하지 않았다. 새 경로에서 `make -C repos/SDLPoP/src -j4`가 통과했다. 게임은 실행하지 않았다.
- 드라이버는 기준 커밋에서 `codex/eink-pop-delay-fix`를 만들었다. 기존 `.local` 원본은 그대로다.
- 사용자 후속 지시 “저장소 처리에 대한 것만 끝나면 나머지는 계획대로 진행”을 확인했다. 저장소 구성 커밋 뒤 지연 수정·제한 시험으로 이어간다. push는 하지 않는다.

저장소 구성은 상위 `a6ac206`으로 커밋했다. 이어 드라이버의 실제 함수 두 줄만 수정해 `86be1ba`로 커밋했다. EOF를 포함한 나머지 바이트는 원본과 같다. 실제 함수를 C로 실행한 호스트 검증에서 원본 조기 종료 111건을 재현했고, 수정본의 경계 198개와 정지 카운터의 하네스 읽기 상한 1개가 모두 통과했다.

새 스케치의 12개 호스트 시나리오가 통과했다. 실제 스케치·모드별 LUT를 사용해 모든 마스크 픽셀, 경계·가드, 시간 제한, 실패 시 패널 미접근, RUN 1회 조건을 확인했다. 읽기 리뷰에서 미세 측정 경계를 정리하고 호스트의 누적 READY 처리·중단 시 대상 재조회도 보완해 모의 검증했다.

최종 빌드는 프로그램 280,869바이트·전역 19,440바이트로 성공했다. 제조사 컴파일 단위 22개 모두 새 `repos/LilyGo-EPD47` 경로를 사용하고 실제 ELF에도 unsigned 경과량 비교가 들어갔다. 앱 281,232바이트의 SHA-256은 `8d1f0a8bfd72774a4ca3fdb54d85f09588761ef4a80cf3dc4a002ccb8b1d2464`다. 기존 제조사 `round` 경고 외 새 경고는 없었다. 구현·테스트·빌드 근거를 커밋한 뒤 승인된 장치 시험을 한 번 실행한다.
