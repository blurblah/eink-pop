## 요청 사항

> 이전 방식의 의도된 중간 좁아짐을 줄이고 갱신 시간의 개선 가능성을 확인한다. 기존 시험의 오류 수정과 추가 최적화를 구분한다. 관련 변경은 작업 브랜치에 로컬 커밋하고 push하지 않는다.

사용자는 지우기·그리기를 하나의 갱신으로 처리하는 최적화 설명 뒤 “진행해”라고 지시했다. 조사·구현·검증은 이 승인으로 수행한다. 보드 화면 출력은 이전에 약속한 대로 준비됐다는 사용자 답변을 받은 뒤 한 번만 시작한다. 답변이 없으면 빌드·업로드 준비 상태를 보존하고 RUN을 보내지 않는다.

## 조사 결과와 가정

- 기준 드라이버는 `86be1ba`, 상위 프로젝트는 `effa2db`다. 원래 제조사 기준은 `50224221fb81a8fcf9068532374b775af84a38d4`다.
- 각 색에 쓰는 15단계 시간 배열이 서로 다르다. 한 공통 시간으로 양극성을 동시에 출력하면 한쪽 조건이 달라지므로 이번에는 사용하지 않는다.
- 대안은 하나의 3상태 마스크와 API에서 흰색 0단계→검정 0단계→흰색 1단계→검정 1단계 순서로 총 30회 주사하는 것이다. 완전 동시 구동이나 주사 횟수 절반 감소로 설명하지 않는다.
- 기존 극성별 시간값·단계 수·각 주사 후 5tick 대기는 유지한다. 같은 극성 사이의 휴지 간격은 바뀌므로 전체 물리 파형이 동일하다고 주장하지 않는다. 공통 진입 대기·세마포어 준비를 한 번으로 묶는 절감만 기대하며 실제 시간은 측정한다.
- 기존 `skip_row(uint8_t)`는 300을 44로 축소한다. 같은 출력 경로에 필요한 값 보존 수정으로 인수 폭을 넓히고 300 전달을 실제 함수 테스트로 검증한다.
- S3는 단일 DMA 버퍼인데 다음 행이 완료 전에 덮어쓸 수 있는 코드 경로가 있다. 버퍼 반환 전에 전송 완료를 기다리고 프레임 종료도 마지막 전송 뒤에 수행하도록 최소 수정한다. 실제 오염이 관찰됐다고 주장하지 않으며 이전 성능과 비교할 때 이 수정도 포함됐음을 기록한다.
- 초기 전체 지우기, 전원 순서·주파수·전압 설정, 기존 흰/검정 시간 배열은 바꾸지 않는다. USB 픽셀 전송·SDLPoP 연동은 이번 범위 밖이다.
- 제공된 스킬 중 이 작업에 직접 적용되는 스킬은 없다. 기존 문서와 테스트로 절차를 보존한다.

## 성공 조건

- [x] 제조사 원본·기존 시험과 SDLPoP를 보존하고 드라이버 후속 작업 브랜치를 만든다.
- [x] 3상태 4bpp 입력에서 0=검정, 1=흰색, 2~F=무동작을 정의하고 전체 폭·유효 y/높이·정렬 입력만 받아들인다.
- [x] 실제 C 함수에서 두 극성의 15단계 교차 순서, LUT·S3 픽셀 순서, 영역 밖 무동작, 마지막 행 300과 DMA 버퍼 수명을 검증한다. 기존 모드·지연 검증도 통과한다.
- [x] 새 스케치는 RUN 한 번, 20초 지연 선행 검사, 최대 12프레임·30초 시작 제한, 종료 후 패널 정지를 유지한다. 첫 프레임은 기존 검정 출력 한 번, 나머지는 교차 API 한 번을 사용한다.
- [x] 기존 격리 환경에서 빌드하고 실제 드라이버 경로·바이너리 해시를 확인한다. 이전 바이너리는 덮어쓰지 않는다.
- [ ] 사용자 관찰 준비 후 현재 장치를 확인해 한 차례 제한 시험을 수행한다. 종료 후 최소 10초 관찰하고 중간 좁아짐·잔상·최종 모양·호출 시간을 기록한다. 효과가 없어도 사실대로 완료 기록한다.
- [ ] 변경을 로컬 커밋하며 push하지 않는다. 원본 로그·빌드·기기 식별자는 제외 규칙을 유지한다.

## 위험 및 롤백

단계 교차는 극성별 휴지 간격을 바꾸며 중간 좁아짐·잔상 개선을 보장하지 않는다. 시간 폭과 DMA 대기 수정도 포함되므로 이전 시험과의 순수한 단일 변경 비교가 아니다. 장시간 부분 갱신의 안전성이 검증된 것이 아니므로 자동 반복·임의 펄스 조정은 하지 않는다.

장치 오류 시 추가 시험을 하지 않고 기존 관찰기의 중단 절차를 따른다. 코드 롤백은 새 드라이버 작업 브랜치와 상위 참조에 한정한다. 직전 `bw_delta` 앱과 출고 백업을 유지하며 실제 복귀는 실행했을 때만 기록한다. 펌웨어 복구가 패널 잔상을 없앤다고 보장하지 않는다.

## 실행 기록

계획 전 읽기 조사에서 서로 다른 극성별 시간표, 마지막 행 인수 축소와 S3 단일 버퍼 재사용 조건을 확인했다. 드라이버·스케치 코드는 아직 변경하지 않았고 장치에 접근하지 않았다.

구현 전 출고 백업 16,777,216바이트와 직전 차분 앱 281,232바이트의 SHA-256이 기존 기록과 일치함을 확인했다. 외부 SDLPoP와 `.local` 제조사 원본의 HEAD·브랜치·상태·diff·파일 해시도 이관 전 기록과 같았다. 드라이버는 `86be1ba`에서 `codex/eink-pop-interleaved-update`를 생성했다. Arduino CLI 1.5.1과 프로젝트 ESP32 코어 2.0.17을 다시 조회했다.

ESP-IDF 4.4.7 공식 API 문서와 로컬 SDK 헤더에서 DMA 완료 이후 버퍼 재사용 계약을 대조했다. GitHub 웹의 고정 커밋 원문은 조회 오류가 있었으므로 실제 구현 판단은 보존된 동일 커밋 로컬 소스를 정본으로 사용했다. 코어·드라이버 업데이트는 하지 않았다.

전용 교차 API와 3상태 LUT·극성 마스크, 마지막 행 시간 폭과 S3 전송 완료 대기를 구현했다. 독립 리뷰에서 발견한 작업 생성 실패의 다른 코어 접근 가능성은 새 작업의 첫 동작을 시작 통지 대기로 바꾸고 두 작업이 모두 생성된 뒤 통지하도록 보강했다. 기존 `epd_draw_image()` 본문과 시간 배열은 유지했다.

실제 C 드라이버 하네스는 clang·AddressSanitizer로 실행해 출력 경로 22개, LUT 65,536개×4픽셀, 무효 입력 19개, 생성 실패 4개, 시작 통지 선행을 통과했다. 원본 300→44와 DMA 중 조기 반환·종료를 재현하고 수정본 통과를 확인했다. 실제 RTOS 동시성·큐 역압·물리 파형은 이 호스트 검증 범위가 아니다. 새 스케치 13개 시나리오, 기존 스케치 12개와 지연 함수 199개 회귀도 통과했다.

최종 빌드 프로그램은 281,941바이트, 전역 19,440바이트다. 앱 바이너리 282,304바이트의 SHA-256은 `4288737380d4f1d33c38d127156fb19a44d372533c87d460ff816656497c0511`이다. 드라이버 컴파일 단위 22개가 모두 `repos` 경로이며 ELF의 새 API·시작 통지·DMA 대기·지연 비교를 확인했다. 기존 `round` 선언 경고 외 새 경고는 없었다. 빌드·호스트 테스트가 같은 실제 소스 해시를 사용함을 대조했다.

관찰기의 새 로그 마커·바이너리 경로와 실제 파일 해시를 대조하고, 누적 READY·정상 종료·실행 후 READY·실패 DONE을 장치 없는 모의 입력으로 확인했다. 업로드와 RUN은 분리하며, 현재까지 새 장치 시험은 실행하지 않았다.
